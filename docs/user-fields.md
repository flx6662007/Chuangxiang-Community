# 用户字段说明表

版本：v1.0，用户已确认的首版建模基线。

本表依据项目方案、邮箱验证方案及本轮用户确认，确定 `accounts.User` 的字段设计，并说明邮箱验证、账号限制和联系方式如何关联。用户已整体确认本表，字段类型、长度、默认值、模型划分及第九节的首版处理方式作为本分支的实现依据；后续按交接流程与后端同步技术衔接，不代表后端已经审阅或成果已经合入主分支。当前已编写用户模型、管理器及基础约束，尚未生成初始迁移或在开发库创建业务表。

单独用于查看或交接的表格见 [用户字段表](user-fields-table.md)。精简表是本文的摘要，字段或规则变更时两份文档同步更新。

## 一 已确认的产品规则

| 事项 | 确认结果 |
| --- | --- |
| 注册与登录 | 使用 `@tongji.edu.cn` 学校邮箱及密码；同一邮箱只能对应一个账号，邮箱去首尾空格并统一小写 |
| 公开身份 | 注册时生成类似 `CX-7K2M9Q4R` 的唯一系统代号；每个账号固定使用，用户不能自行修改；公开页面不展示邮箱或其他联系方式 |
| 邮箱绑定 | 首期每个账号绑定一个学校邮箱；验证后不开放自助换绑，特殊情况由管理员处理，新邮箱必须重新验证 |
| 未验证账号 | 可以登录、查看公共内容和自己的账号状态、重发验证码；不能发布招募或提交申请 |
| 邮箱验证状态 | 以 allauth 的邮箱验证记录为唯一来源，不在用户表中维护第二份验证状态 |
| 业务限制 | 新增招募和提交新申请一起限制；每次固定 24 小时，到期自动恢复，管理员可以提前解除 |
| 受限期间 | 保留登录、查看已有记录、申请退出和申诉能力；已有成员关系继续保留 |
| 联系资料填写 | 注册时保存学校邮箱；首次发布招募或提交申请前，微信号、手机号至少填写一种，允许两种都填，保存到账户并支持后续修改 |
| 联系资料展示 | 发起人接受申请后，仅向具有联系权限的对应另一方展示学校邮箱及已填写的微信号、手机号；申请结束、退出或移除完成后隐藏 |
| 联系资料修改 | 当前仍有联系权限的对象同步看到最新值；不继续展示此前保存的旧版本 |
| 账号关闭 | 首期不提供自助注销，由管理员处理关闭与个人资料处理申请 |

学校邮箱验证仅说明邮箱使用权，页面统一使用“学校邮箱已验证”。手机号目前只是联系资料，首期不新增短信认证或手机号登录。

## 二 数据归属与实施阶段

本版将账户基础与额外联系资料统一放在 `accounts.User`，不增加一张只有两个联系方式字段的资料表。

| 模型或关系 | 用途 | 实施阶段 |
| --- | --- | --- |
| `accounts.User` | 账号基础、系统代号、微信号和手机号、Django 基础权限 | 第一轮建立；联系方式在注册时可空，发布与申请时的检查随组队功能接入 |
| Django `Group`、`Permission` 及用户的多对多关系 | 学生管理员等后台权限分配 | 保留 Django 机制，具体权限随功能配置 |
| allauth `EmailAddress` | 学校邮箱归属、主邮箱及验证状态 | 后端接入并锁定 allauth 版本时，由其迁移创建 |
| `accounts.UserRestriction` | 记录每次 24 小时业务限制和提前解除 | 本表先明确字段；治理功能接入时建表，不阻塞第一轮用户基础模型 |
| 队伍、申请、成员、收藏、举报、申诉等模型 | 通过外键关联用户 | 对应业务阶段实现，不存为用户表中的数组或角色标签 |

自定义用户继承 `AbstractUser`，移除 `username`、`first_name`、`last_name` 字段，以 `email` 为登录标识；配套自定义用户管理器、后台表单，并将依赖姓名或用户名的显示方法适配为系统代号。首次迁移前设置 `AUTH_USER_MODEL = "accounts.User"`，自定义用户必须在 `accounts` 的首次迁移中创建。参见 [Django 5.2 自定义用户说明](https://docs.djangoproject.com/en/5.2/topics/auth/customizing/)。

## 三 用户表字段

模型：`accounts.User`；表名沿用 Django 默认的 `accounts_user`。

下表的类型、长度和默认值为本版确定值。`NULL` 表示数据库空值；可选字符串统一用空字符串 `''` 表示未填写，不同时使用两种空值。时间使用带时区的时间值，界面按 `Asia/Shanghai` 展示。

| 字段名 | 含义 | Django 类型 / PostgreSQL 类型 | 必填、空值与默认值 | 唯一性及写入规则 | 可见范围 |
| --- | --- | --- | --- | --- | --- |
| `id` | 用户内部主键 | `BigAutoField` / `bigint` | 系统自动生成，不允许 NULL | 主键；创建后不修改 | 内部关联或必要的接口引用；公开称呼使用系统代号 |
| `email` | 学校邮箱、登录标识、邮箱联系资料来源 | `EmailField(max_length=254)` / `varchar(254)` | 注册必填；不允许 NULL 或空字符串；无占位默认值 | `unique=True` 并增加忽略大小写的唯一约束；去首尾空格、全小写；普通用户不能通过资料编辑接口修改 | 本人、授权管理人员；获得联系权限的对应另一方 |
| `password` | Django 密码哈希及算法信息 | Django 内置 `CharField(max_length=128)` / `varchar(128)` | 注册时提供原始密码，由 Django 生成存储值；不允许 NULL | 不要求唯一；只能通过 Django 密码处理接口写入，不能直接保存明文 | 所有客户端接口均不返回；管理员也不展示哈希 |
| `public_code` | 公开系统代号 | `CharField(max_length=11)` / `varchar(11)` | 注册时系统生成；不允许 NULL 或空字符串 | 唯一；格式为 `CX-` 加 8 位大写字母或数字；碰撞时重新生成；客户端不可指定或修改 | 可随公开招募等业务内容展示；不建立学生资料浏览目录 |
| `wechat_id` | 微信号 | `CharField(max_length=64, blank=True, default='')` / `varchar(64)` | 注册时可空字符串；不允许 NULL | 不设唯一约束；去首尾空白；用户可修改；保存微信号文本，不保存二维码、链接或图片 | 本人、具备处理权限的管理人员、获联系权限的对应另一方 |
| `phone_number` | 联系手机号 | `CharField(max_length=32, blank=True, default='')` / `varchar(32)` | 注册时可空字符串；不允许 NULL | 不设唯一约束；用字符串保留国家区号；用户可修改；格式校验由前后端统一，不宣称号码归属已验证 | 同 `wechat_id` |
| `contact_updated_at` | 最近一次联系资料变更时间 | `DateTimeField(null=True, blank=True)` / `timestamptz` | 默认 NULL；首次补充微信或手机号后由系统写入 | 后续微信、手机号变更或学校邮箱换绑成功时更新；用户不可直接提交 | 本人、授权管理人员；不在公开卡片中返回 |
| `is_active` | 账号是否启用 | `BooleanField(default=True)` / `boolean` | 不允许 NULL；默认 True | 由授权管理员处理停用；邮箱未验证或 24 小时业务限制均不改变此字段 | 本人和授权管理人员 |
| `is_staff` | 是否具备 Django 管理后台入口资格 | `BooleanField(default=False)` / `boolean` | 不允许 NULL；普通用户默认 False | 仅授权管理员设置；仍需配套具体操作权限 | 授权管理人员；必要时用于本人后台入口判断 |
| `is_superuser` | Django 超级管理员标记 | `BooleanField(default=False)` / `boolean` | 不允许 NULL；普通用户默认 False | 仅可信的管理员创建和授权流程设置；学生内容管理员不默认开启 | 授权管理人员；不作为公开资料 |
| `date_joined` | 账号创建时间 | `DateTimeField(default=timezone.now)` / `timestamptz` | 不允许 NULL；创建时自动生成 | 创建后不由普通用户修改 | 本人和授权管理人员 |
| `last_login` | 最近一次成功登录时间 | Django 内置 `DateTimeField(null=True, blank=True)` / `timestamptz` | 默认 NULL，表示尚无登录记录 | 认证流程维护；不是最后浏览或操作时间 | 本人和授权管理人员 |

密码、权限标记和登录时间沿用 Django 认证字段的职责，具体长度也已核对本机 Django 5.2.17。参见 [Django 用户与权限字段](https://docs.djangoproject.com/en/5.2/ref/contrib/auth/)。

### 用户组与具体权限

下列关系不存为 `accounts_user` 的普通列，由 Django 管理关联表。

| 关系字段 | 类型 | 默认值与作用 | 谁可修改 |
| --- | --- | --- | --- |
| `groups` | 到 Django `Group` 的多对多关系 | 默认为空；建议用“学生管理员”等组统一分配内容维护、举报处理等权限 | 授权管理员 |
| `user_permissions` | 到 Django `Permission` 的多对多关系 | 默认为空；按需授予特定权限，优先通过用户组维护 | 授权管理员 |

队长、申请人、成员由具体队伍和申请关系确定；同一个用户可以在不同队伍中承担不同角色，不新增全局 `role=leader/member` 字段。

## 四 学校邮箱验证关联

复用 allauth 的 `EmailAddress`。下表只定义项目需要的含义；实际主键类型、列长度、索引及迁移以最终锁定的 allauth 版本为准，不手工重建或改造第三方表。

| 字段 | 类型或关系 | 项目中的含义 | 写入与读取规则 |
| --- | --- | --- | --- |
| `id` | 第三方模型主键 | 邮箱记录标识 | 由 allauth 管理 |
| `user` | 到自定义用户的外键 | 邮箱属于哪个账号 | 关联 `settings.AUTH_USER_MODEL`；不关联 Django 默认用户表 |
| `email` | 邮箱字符串 | 需要验证的邮箱 | 当前生效的主邮箱应与 `User.email` 一致，并使用同样的规范化规则 |
| `verified` | 布尔值 | 该邮箱是否完成验证 | 新邮箱默认未验证；只有正确的验证流程才能置为 True；不接受客户端直接修改 |
| `primary` | 布尔值 | 是否为当前主邮箱 | 正常状态只有一个当前绑定主邮箱；管理员换绑流程保持一致性 |

项目允许一个当前绑定学校邮箱；allauth 的原生用户与邮箱关系仍可为一对多。管理员换绑所需的临时待验证记录不等于第二个已经生效的绑定邮箱。接入时统一处理 `User.email`、主邮箱标志和验证记录，避免只修改一个字段。

当前决定允许未验证账号登录。allauth 文档中 `optional` 邮箱验证允许这种登录并发送验证邮件；这不代表放开发布和申请，项目仍需在业务接口中检查邮箱验证。验证码交互、重发及换绑应在锁定版本后实际联调。参见 [allauth 邮箱验证与配置](https://docs.allauth.org/en/latest/account/configuration.html)。

第一轮尚未接入 allauth 时，不创建虚假的已验证状态，也不因当前验证表尚未建立而在 User 中临时加一个验证布尔值。

## 五 业务限制记录字段

模型：`accounts.UserRestriction`；表名 `accounts_userrestriction`，治理阶段实现。一个用户可对应多条历史限制记录；当前是否受限由有效记录计算，不在 User 中重复维护 `is_restricted` 或另一份截止时间。

| 字段名 | 含义 | Django 类型 / PostgreSQL 类型 | 空值及默认值 | 约束与维护方式 |
| --- | --- | --- | --- | --- |
| `id` | 限制记录主键 | `BigAutoField` / `bigint` | 自动生成，不允许 NULL | 主键 |
| `user` | 被限制的用户 | `ForeignKey(User, on_delete=PROTECT)` / `bigint` | 必填，不允许 NULL | 同一用户可有多条历史记录；不因账号停用删除历史 |
| `reason` | 限制原因 | `CharField(max_length=500)` / `varchar(500)` | 必填，无默认占位值 | 管理员填写必要原因；本人及授权管理员可读，不公开 |
| `starts_at` | 限制生效时刻 | `DateTimeField` / `timestamptz` | 必填，创建限制时由系统赋当前时间 | 首版即时生效，不开放预约处罚 |
| `expires_at` | 原定到期时刻 | `DateTimeField` / `timestamptz` | 必填，由系统计算 | 固定等于同一次计算的 `starts_at + 24 小时`，管理员不直接编辑时长 |
| `created_by` | 作出限制的管理员 | `ForeignKey(User, on_delete=PROTECT)` / `bigint` | 必填，无默认用户 | 从当前有权限的操作者确定，不能由客户端伪造 |
| `revoked_at` | 提前解除时间 | `DateTimeField(null=True, blank=True)` / `timestamptz` | 默认 NULL | 提前解除时写入；自然到期不需要填写 |
| `revoked_by` | 提前解除的管理员 | `ForeignKey(User, on_delete=PROTECT, null=True, blank=True)` / `bigint` | 默认 NULL | 与 `revoked_at` 一起写入；按管理员权限校验 |
| `revoke_reason` | 提前解除原因 | `CharField(max_length=500, blank=True, default='')` / `varchar(500)` | 初始为空字符串 | 人工提前解除时必填，保留原始限制记录 |

每个到用户的外键需设置不同的反向关系名。所有限制记录只允许目标本人和具备处理权限的管理人员访问；向本人展示原因与时间，不必暴露管理员的私人联系方式。

有效限制的判断规则为：`starts_at <= 当前时间 < expires_at`，且 `revoked_at IS NULL`。到期时判断自然变为不受限，无需等待定时任务修改一个布尔值。提前解除填写撤销字段，不回写或抹掉原定截止时间。

添加 `(user, expires_at)` 查询索引，以及截止时间固定为生效后 24 小时、解除时间与操作人同时有值或同时为空等约束。限制期间重复点击处理同一账号，默认返回当前有效记录，不叠加、不重置 24 小时；事务内锁定目标用户，防止并发重复创建。具体实现随治理功能与后端对齐。

## 六 计算得到的状态

以下可作为账号状态接口的返回值，但不增加同名数据库列。

| 名称 | 数据来源与含义 | 使用范围 |
| --- | --- | --- |
| `school_email_verified` | 当前 `User.email` 对应的 allauth 主邮箱记录已验证，且属于允许域名 | 本人状态、公开卡片上的“学校邮箱已验证”标记、服务端权限检查 |
| `has_contact_details` | 规范化和校验后的微信号、手机号至少有一项已填写 | 本人提示及发布、申请前检查；学校邮箱本身不能代替额外联系资料要求 |
| `is_restricted` | 是否存在第五节定义的当前有效限制记录 | 本人状态、管理员处理及服务端权限检查 |
| `restriction_ends_at` | 当前有效限制记录的截止时间；无有效限制时为空 | 本人及授权管理员，不公开 |
| `can_publish`、`can_apply` | 账号层面满足登录、启用、学校邮箱已验证、未受限且联系资料已补齐 | 本人界面提示；实际接口还必须校验赛事、队伍、名额、重复申请等对象和业务规则 |

接口中的验证标记只能由后端计算。发布与申请每次请求都需重新检查，不能仅在用户第一次操作或前端按钮显示时检查。

## 七 联系资料的读取与修改

1. 注册邮箱保存在 `User.email`，不增加重复的 `contact_email` 字段。
2. 微信和手机号分别保存，允许两项都有；不需要再设置只能二选一的 `contact_type` 或首选渠道。
3. 发布或提交申请前要求微信、手机号至少一项通过格式校验；仅有学校邮箱仍需补充。
4. 发起人接受申请后，仅在发起人与对应申请人之间开放联系资料；正式入队后该对应联系权限保留，其他队友不会自动获得查看所有人联系方式的权限。
5. 有效联系权限下返回当前学校邮箱及已填写的微信、手机号；对空值可不展示，但不能用邮箱前缀替代系统代号。
6. 用户修改资料后，仍有联系权限的对应另一方读取最新值；不把首次解锁时的联系方式复制进申请或成员表作为后续展示来源。
7. 申请撤回或终止、成员退出或移除完成后，不再返回联系方式。招募卡关闭本身不撤销已有成员关系的联系权限。
8. 公开接口使用明确的字段白名单；私有联系资料由检查了当前关系权限的接口返回，不能先给前端再隐藏。

联系资料字段在数据库层允许为空，因为注册时尚未补充；“至少填写一种”属于发布与申请时的条件校验，不添加阻止空资料注册的全表检查约束。

## 八 约束与校验清单

| 对象 | 数据库层 | 后端输入及业务层 |
| --- | --- | --- |
| 学校邮箱 | 非空、非空字符串；普通唯一约束加 `Lower(email)` 函数唯一约束；建议增加存储值已去首尾空格且为小写的检查 | 全路径使用 `strip().lower()`；校验邮箱格式和精确域名 `tongji.edu.cn`，不能用模糊字符串包含判断；注册、管理命令及换绑都执行 |
| 系统代号 | 非空、唯一、最大长度 11；建议检查 `CX-` 加 8 位大写字母或数字的格式 | 系统随机生成；唯一冲突时有限重试；注册和资料接口禁止传入代号覆盖生成值 |
| 密码 | 使用 Django 内置存储字段，不额外保存原始密码 | 使用 `set_password` 或认证组件的等效安全入口；执行项目密码校验；所有读接口排除密码字段 |
| 微信与手机号 | 允许空字符串、不允许 NULL；各自限制长度；不设唯一约束 | 去除无意义首尾空白，校验格式；发布和申请时至少一项有效；只允许修改自己的资料 |
| 24 小时限制 | 时间与解除字段成对一致；记录关联有效用户和操作者 | 仅有权限的管理员可创建或解除；同一操作中计算开始与到期；每次请求判断是否已到期 |
| 管理权限 | 默认使用 Django 的关联表和布尔字段 | 普通用户不能写入 `is_staff`、`is_superuser`、`groups`、`user_permissions` 或限制记录 |
| 邮箱验证 | 使用 allauth 自带迁移及约束，并保留 User 自身唯一性要求 | 验证状态不可由客户端直接写入；当前生效主邮箱与 User.email 一致；换绑的新邮箱重新验证 |

忽略大小写的唯一性由数据库承担，避免仅靠注册接口规范化而被其他写入路径绕过。Django 支持基于 `Lower` 表达式的唯一约束，见 [Django 约束说明](https://docs.djangoproject.com/en/5.2/ref/models/constraints/)。普通 `email` 唯一约束同时便于其作为 Django 登录标识；不再为已有唯一索引的列重复增加相同普通索引。

## 九 首版边界处理

本节处理方式随用户对字段表的整体确认一并纳入 v1.0。认证接口和账号关闭流程的实现细节在对应阶段与后端集中对齐，不阻塞用户基础模型。

| 场景 | 首版处理方式 |
| --- | --- |
| 未验证邮箱再次注册 | 不创建第二个账号，不覆盖已有账号密码或资料；引导走登录、验证重发或密码找回流程，具体响应和限流由认证模块统一处理 |
| 长期未验证账号 | 先不自动删除或释放邮箱；后续再明确清理周期，避免字段建设阶段引入自动删除 |
| 管理员邮箱换绑 | 新邮箱验证成功后，在受控流程中切换 User.email 与主邮箱记录；成功前保留旧绑定；同步更新联系资料时间，不把旧邮箱的已验证状态直接复制给新邮箱 |
| 联系资料全部清空 | 注册时两项都可为空；首次补齐后，普通资料编辑至少保留一种；关闭账号时的个人资料处理走管理员流程 |
| 关闭账号 | 先停用登录并使已有会话失效，保留关联记录和原邮箱占用，不物理删除用户；联系资料处理及未结束队伍关系由管理员按具体申请处理，后续补充完整规则 |
| 手机号格式 | 字符串存储，允许携带国家区号；规范化规则与前端一致，不自动假定所有用户都是中国大陆号码，不将格式通过等同于号码归属已验证 |
| 学生管理员 | `is_staff=True` 配合必要用户组权限；不默认设为超级管理员 |

联系方式同步读取规则已确认。邮箱换绑涉及身份与联系信息同时变化，后端需把它作为单独流程实现，不能当作普通个人资料字段直接更新。

## 十 实施与验收

### 第一轮交接顺序

1. 将本表同步后端，对齐邮箱登录、自定义用户配置、allauth 关系及管理员创建方式；说明新增手机号和未验证可登录的规则。
2. 整理赛事字段说明表，对齐赛事与届次、发布状态、来源和各类日期的含义及可空规则。用户与赛事字段目前均已交付，对应第一轮模型已编写。
3. 数据库负责人实现 `accounts.User` 与约定的赛事模型，配套用户管理器；与后端衔接 Admin 表单及账号配置。自定义用户可以先编写，无需等真实邮件服务。
4. 设置 `AUTH_USER_MODEL`，确保 `accounts.User` 在首次迁移中创建；生成并检查模型对应迁移，再在空开发库应用迁移，创建管理员并验证数据约束。
5. 准备可重复导入的虚构赛事数据，覆盖已发布、草稿、日期缺失及超过一页的已发布记录。
6. 补充数据库初始化说明与验证结果，模型、迁移、样例导入和文档一起提交当前任务分支，并按团队流程提交 PR。后端据此开发赛事接口，前端接入。

allauth Headless、验证码发送和登录接口由后端负责接入；业务限制和联系方式解锁按对应业务阶段实现。当前实现了用户模型和管理器，尚未执行开发库迁移。`User.save()` 会规范化并校验基础字段、维护联系资料更新时间，系统代号冲突最多尝试 5 次；`create_user` / `create_superuser` 使用密码强度校验及 Django 哈希接口。微信号的基础字符校验允许字母、数字、下划线和短横线；手机号允许开头的 `+`、数字、空格、括号和短横线，不代表归属验证。普通用户字段权限、补齐后不允许自行清空所有联系资料、邮箱换绑及会话处理属于后续认证和资料接口，不能把直接 ORM 写入当作这些接口。

### 最小验收案例

| 阶段 | 应覆盖的案例 |
| --- | --- |
| 用户模型与数据库 | 正常创建用户；空邮箱拒绝；大小写不同的重复邮箱拒绝；绕过表单写入也不能制造重复；密码不以明文保存；系统代号唯一且不可由普通用户改写；未补联系方式仍能创建账号 |
| 联系资料与组队接口 | 微信、手机号仅填一项或同时填写均可；两项都空不能发布或申请；资料修改后有效联系对象读取最新值；公开接口及无联系权限对象拿不到这些字段；关系结束后不再返回 |
| 邮箱与登录 | 新账号未验证；未验证仍可登录但不能发布或申请；正确验证后以 allauth 状态为准；换绑不能继承旧邮箱的验证结果 |
| 业务限制 | 同时拦截新增发布和申请；保留已有记录及退出、申诉能力；24 小时边界前后判断正确；提前解除立即恢复相应能力；重复管理员操作不意外延长处罚 |
