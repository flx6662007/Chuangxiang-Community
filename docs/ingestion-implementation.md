# 赛事持续采集

更新：2026-09-28。当前按 `backend/competition_catalog/data/tongji-2026.json` 的 **255 项学校目录**采集，覆盖全部学科。代码分为 `backend/competition_catalog/` 的通用官网监测和 `backend/ingestion/` 的结构化适配。采集在后台命令中运行；用户打开页面时直接读取已保存的赛事卡片。

本轮实网运行与增量验证仍在进行。抓取成功数量、调度启用、最终验证与 GitHub 状态由 [团队进度](progress.md) 统一记录；不把目录登记数量当作成功抓取或公开数量。

## 两条处理链路

```text
学校目录 255 项
  → init_competition_catalog 登记目录和已核对官网
  → sync_competition_catalog 按到期时间读取官网
  → 保存后台通知、入口快照、原文版本和失败原因
  → 后续按具体官网完善提取与核对规则

已有 AIC / NCDA 专用适配器
  → sync_competitions 发现、复查官方通知
  → 原文版本 → 字段候选与证据 → 受控采纳
  → 关联目录 → 保存结构化赛事
  → 前端读取卡片和详情
```

通用监测不直接写公开赛事，不设置报名日期、队伍人数或招募权限。正文能够抓到，只表示取得了供后台核对的资料。专用适配器才负责赛事字段提取；取得网页、完成核验和允许发布是不同步骤。

## 目录与官网监测

### 范围和数据

| 模型 | 作用 |
| --- | --- |
| `CatalogEntry` | 保存目录编号、原名、年份、目录等级、责任学院及已核实别名，不含教师姓名或工号 |
| `OfficialSite` | 保存官网入口、关联证据、域名白名单、启用状态、最近结果和下次检查时间 |
| `OfficialNotice` | 保存通知或入口快照的正文版本、附件链接、明确发布日期及待处理状态 |
| `MonitorRun` | 记录每次监测成功页数、新版本、未变化数量与失败原因 |
| `CatalogBinding` | 将已发布赛事关联到目录中的赛事系列 |

只登记经核对的赛事官网、主办方或校内官方入口。多个目录条目可以共用网站，同轮复用成功响应。初始官网关系来自版本化目录配置，网页链接不能自行扩充白名单。后台这些模型均为只读，不提供任意网址录入或直接发布入口。

目录中的赛事系列包含多个子赛，不表示全部子赛奖项均获学校同等认定。目录年份、官方赛事届次、校内政策和报名阶段分别保留。当前公开范围按启用目录关联筛选，不按学科排除人文社科或艺术类。

### 获取与版本

- 读取启用且到期的官网，跟随已核对域名内相关通知。综合站按赛事名称及已核实别名筛选；赛事专站可按通知、报名、规则等标题发现页面。
- 每个入口默认每轮最多 3 页，包含入口本身。详情按尝试与成功读取时间轮换，避免失败页面持续占用全部预算。
- 可保存入口快照和通知正文。附件只记录链接；当前通用监测不解析扫描 PDF、图片、Word 或压缩包，不把附件存在视为已读其内容。
- 明确发布日期才写入 `source_published_on`；首次发现和最近读取时间另存，不替代发布日期。标题或日期可识别为往届时标记历史，未知年份不猜。
- 相同入口、URL 和内容哈希复用版本；正文变化保留新旧版本。A→B→A 回退重新指向版本 A，不重复造相同正文。
- 动态空页面、登录页、访问验证、robots 限制和网络失败记录异常，不绕过限制。异常不删除已有通知或赛事。
- 来源级 PostgreSQL 锁防止同一入口并发执行；正常读取后约 6 小时复查，失败退避最长 72 小时。锁冲突直接跳过。

后台结果 `succeeded`、`snapshot_only`、`partial`、`failed` 分别表示成功、仅有入口快照、部分失败和失败；它们不是赛事发布状态。原文的“待提取核对／关键内容在附件／往届资料”也不表示当前可报名。

### 手动运行

在 `backend` 目录、PostgreSQL 可用且迁移已执行后运行：

```powershell
# 登记目录及已核对官网；检查既有 AIC/NCDA 赛事的目录关联。
.\.venv\Scripts\python.exe manage.py init_competition_catalog

# 检查启用且到期的官网，默认最多 300 个入口、每入口 3 页。
.\.venv\Scripts\python.exe manage.py sync_competition_catalog

# 单独复查一个目录赛事；force 仅忽略到期时间，不绕过 robots。
.\.venv\Scripts\python.exe manage.py sync_competition_catalog --code 2026020 --force --max-pages 3
```

`--code` 可重复；`--limit` 为 1–500 个入口；`--max-pages` 为每入口 1–10 页。命令逐项输出状态，部分失败以非零退出码结束，但其他成功记录已保存。初始化不创建账号、不授予权限，也不恢复人工停用的入口；配置中撤销的错误官网停止轮询，已有原文保留。

## 字段提取

AIC 正文使用 `.article-content`，NCDA 使用下述固定表格。标题、年度和发布日期取专用正文或元信息区，导航、页脚和抓取时间不能作为依据。

| 字段 | 处理方式 |
| --- | --- |
| 名称、年度、届次、赛项 | 从具体通知识别，同系列新届次独立建档，不覆盖旧届 |
| 主办方、资格、人数 | 只取明确条款；教师人数不计入学生人数，同校、跨校及选拔限制随条款保留 |
| 简介、详情、方向 | 由已提取事实形成说明，保留资格与报名方法，公开页面不复制整篇公告 |
| 报名和作品截止 | 分别读取明确年月日；没有依据保持 `null`，不从首页“报名中”推断 |
| 截止时刻、时区 | 未明确时区时不写精确时间，原文小时留在 `deadline_notes`；不自动补为 23:59:59 |
| 报名入口 | 采用官方正文或导航明确链接并保留证据，不访问报名系统或代用户报名、付款 |
| 分类 | 平台栏目分类，不冒充官方奖项等级或学校奖项认定 |
| 校内安排和未知字段 | 没有校内来源就留空，前端显示对应缺项说明 |

`--enable-recruitment` 仅对**新收录**且明确可组队、人数上限和未来报名日的赛事生效。平台按北京时间在官方报名截止日期前一天 00:00 提前停招，内部 `recruitment_note` 记录依据；这不是官方报名截止时刻。人工停招不会被下次同步自动打开。

### NCDA 口径

- 在 `#main .dsjs` 内解析 `table.peixun_table`，按标签读取并处理 `rowspan`。年度来自正文赛事横题或赛项名称，编码包含年度及赛项代码。
- 9B6、9B8、9C3 原文分别给出 **2026-09-30、2026-09-22、2026-10-31** 作品投稿截止，只写 `submission_deadline`，独立报名截止保持空。学校审核、获奖公布、国赛阶段另存说明。
- 首页“征稿中”只用于发现；9B8 已于 9 月 22 日截止。页面离开首页后，已收录原文仍继续轮换复查。
- “每件作品最多三名作者”是作者限制，不直接当队伍上限；教师人数不计入队员。上述三项暂不自动开启组队招募。
- 原文没有发布日期、时区或报名截止时保持缺项；不以抓取日期补写。
- NCDA 接入沿用现有全局规则版本 `v2`，避免为未变化的其他来源重复制造候选。

## 采纳与变更

结构化采集依次保存 `FetchRun` 获取记录、`SourceVersion` 不可变原文和 `ProcessingResult` 字段候选。网络请求在业务事务外完成，采纳与候选状态在同一短事务提交，失败整体回滚。

- 相同来源、URL 和规范化正文哈希复用版本，不刷新原通知日期、首次发布时间或赛事内容更新时间。
- 正文变化创建新版本。官网 A→B→A 回退虽复用正文 A，仍新增待复核处理记录；历史采纳决定不能直接复用。
- 采纳前核对最近观察版本，旧候选不能覆盖新信息。官网复用同一 URL 发布新届次时留待处理，不能把原赛事改成新届次。
- 自动采纳记录规则版本 `official-html-2026-09-v2`。新赛事须有明确身份、主办方和资格；未知人数或日期不会自动开启招募。升级提取规则可为同一正文生成新候选，重要字段补全仍须复核。
- 已有记录仅允许未被人工改动的说明性字段自动更新。日期、人数、资格、报名链接等重要变化待复核；缺项和网络失败不清空旧内容。
- 管理员采纳重要变化会停止该赛事招募，使用统一赛事事务服务结算受影响申请；重新核对后再开启。
- 同一截止条款含多个日期或延期措辞时不直接取第一个日期。教师、学生人数混杂或不同组别上限冲突时停止自动采纳。AIC 仅在明确允许单人时记录下限 1 人。
- PostgreSQL 来源级锁防止重复触发。进程退出后锁释放；遗留的 `running` 记录只在下一进程取得对应锁后标记中断。

## 结构化采集命令

须已有获授权的维护账号；将 `维护账号ID` 替换为实际数字，不在命令或仓库中写密码。

```powershell
# 首次登记当前目录内的内置适配来源并运行。
.\.venv\Scripts\python.exe manage.py sync_competitions --init-sources --actor-id 维护账号ID --trigger manual --auto-accept --enable-recruitment

# 后续运行：沿用各来源维护人的权限，目录外来源自动跳过。
.\.venv\Scripts\python.exe manage.py sync_competitions --trigger scheduled --auto-accept --enable-recruitment

# 只检查 AIC，不自动采纳，最多获取 10 篇。
.\.venv\Scripts\python.exe manage.py sync_competitions --source aicomp --actor-id 维护账号ID --trigger manual --max-pages 10
```

`--source` 可重复；每来源默认最多 20 篇，范围 1–50。结果包含发现、获取、未变化、采纳、待处理、失败及锁竞争情况；实际失败返回非零退出码并保留其他成功结果。初始化不覆盖已有维护人、配置或停用状态。

Django Admin 可查看 `SourceConfig`、`FetchRun`、`SourceVersion`、`ProcessingResult`。内置来源通过白名单登记，界面可停用；原文、候选与日志只读。待处理候选通过专用采纳或拒绝操作处理，不直接编辑 JSON。更改提取逻辑须修改适配器与规则版本，再次采集验证。

## 调度与请求边界

Windows 每 6 小时任务需要分别运行官网监测和结构化同步命令；安装方法见 [本机定时任务](maintenance.md)，本轮实际启用与执行结果以团队进度为准。电脑须开机并满足任务所需登录状态，PostgreSQL 与网络须可用；关机或休眠时不能保证更新。迁往服务器后可用等效 systemd timer，无需先引入 Redis。

安全客户端限制超时、重试、重定向、正文大小和同站频率。每跳检查域名白名单及 robots；不会执行原文脚本，不绕过访问验证，也不会自动调用模型。

连接固定到已核验的公网 IP，保留原域名 Host、TLS SNI 与证书验证，避免 DNS 二次解析重绑定。TUN 代理虚拟地址场景可使用固定公开 DNS 查询；仍禁止本机、私网和元数据地址，不关闭 TLS 校验。技术依据见 [HTTPX SNI 扩展](https://www.python-httpx.org/advanced/extensions/#sni_hostname)。

没有模型密钥也能完成现有监测和规则采集。公众号授权同步、附件解析、动态站适配及复杂规则冲突需要后续单独开发；未知信息保留缺项。
