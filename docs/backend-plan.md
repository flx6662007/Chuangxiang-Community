# 后端开发方案

更新：2026-09-26。依据参考 UI 调整栏目和开发顺序；本文是**待实现方案**，不代表新增接口已经上线。现有接口以 [API 说明](api.md) 为准，业务规则以 [产品范围](product-scope.md) 和 [字段说明](database-fields.md) 为准。

## 1. 本轮目标

先完成“查看赛事 → 发布招募 → 申请与联系 → 双方确认入队”的业务闭环，并让赛事数据能够后台持续更新。保留已经实现的账号能力，暂停真实 SMTP 发信接入；本机联调用测试账号和控制台验证码，不删除权限检查，也不把开发验证方式开放给真实用户。

| 阶段 | UI 栏目 | 后端交付 |
| --- | --- | --- |
| M1 | 首页、赛事中心、赛事详情 | 复用赛事查询；补分类词表和必要筛选；首页组合少量已发布赛事，无须单独建“首页内容表” |
| M1 | 团队广场、发布招募、我的组队、通知 | 固定模板发布、申请、联系授权、双方确认、编辑挂起、退出/移除/解散及期限结算；通知只传递系统事件 |
| M1 | 页面背后的赛事同步 | 接入 2～3 个经确认可用的官方来源；每 6 小时检查，支持命令行手动触发；校验候选后入库 |
| M2 | 创享资讯、资源中心、收藏 | 创享资讯收录科研机会与俱乐部快讯；资源由管理员维护外链；收藏赛事、科研和资源 |
| M3 | 智能助手 | 基于平台已公开且已核验内容的只读问答，附原文来源；功能完成并验收后再开放入口 |

截图中的全国赛事数量、参与学生数量、合作机构数量、阅读量均不是现有数据。首页先不提供这些统计；后续确有指标需求，再明确统计口径。站内“加入队伍”不等于赛事官方报名；报名按钮跳转已核验的官方入口。

## 2. 现有基础与缺口

| 模块 | 已有内容 | 本轮要补的内容 |
| --- | --- | --- |
| `accounts` | allauth 浏览器 Session、注册登录、开发验证码、本人资料和账号门槛 | 新业务复用门槛与对象权限；真实 SMTP 延后 |
| `competitions` | 模型、已发布赛事列表/详情、Admin 维护和来源核验、发布/下架服务 | 筛选词表、组队联动下架/停止招募、供采集使用的受控导入入口 |
| `teams` | 队伍、招募、申请、成员、退出/移除、解散、历史版本与字段校验 | 查询、事务服务、接口、到期结算；已有样例导入不能充当正式业务服务 |
| `notifications` | 业务事件及收件人通知模型 | 随业务状态同事务写入，个人列表与已读接口 |
| `ingestion` | 来源配置、获取记录、原文版本、候选结果、AI 调用追溯模型 | 来源适配器、调度命令、幂等写入、候选处理、运行记录界面 |
| `research`、`newsletters`、`resources`、`favorites` | 数据模型、迁移和约束 | M2 的公开读取、Admin 维护、收藏接口及权限 |
| `ai_services` | 通知提取、快讯草稿、模型客户端、校验与异常处理 | 接到采集候选流程；没有直接可用的聊天机器人接口 |

现有业务数据库已经建立各模块模型及其关系。继续使用已有模型和迁移；不因参考 UI 推倒重建。确有字段缺口时，先由前端、后端、数据库同学确认含义，再新增迁移并同步字段表。

## 3. 技术与目录

| 用途 | 采用方式 | 原方案调整 |
| --- | --- | --- |
| HTTP 接口与业务 | Django + DRF | 保持现有选型；查询与事务分开，禁止给所有模型直接开放任意增删改查 |
| 身份与权限 | django-allauth Headless + Session Cookie + CSRF | 继续使用现有实现；暂停 SMTP 不等于取消登录、邮箱与联系方式门槛 |
| 数据 | PostgreSQL + Django ORM/迁移 | 保留约束；跨表状态与并发由事务服务保证 |
| 抓取与正文提取 | 现有 HTTPX；接入来源时增加 Beautiful Soup | 先处理结构稳定的页面，不为截图引入整套浏览器采集服务 |
| 定时执行 | Django 管理命令 + Windows 任务计划；部署后可用 Linux systemd timer | M1 不引入 RQ 采集队列；需要后台排队、重试和多工作进程时，再评估原方案的 RQ + Redis |
| 测试 | 现有 Django/DRF 测试，加 PostgreSQL 事务并发测试 | 不因调整 UI 重写为 pytest；原方案中的 pytest 可另行评估 |
| 接口文档/校验 | 现有 DRF Serializer、校验函数、`docs/api.md` | Pydantic、drf-spectacular 不是本轮必装依赖；出现明确维护需要再引入 |
| 部署 | 当前 Windows 本机；已有 Linux Docker Compose + Caddy 部署准备 | 以仓库现有 Caddy 配置为准，不再重复准备 Nginx；部署方案中的 Redis 用于共享限流，与是否启用任务队列是两件事，当前未公网部署 |
| AI | 复用 `ai_services`；服务端配置模型与密钥 | Qwen 是候选，具体型号尚未选定；用真实通知样本评测后确定，不新增本地大模型或向量库 |

建议按已有应用继续组织代码，以下均为要补充的文件职责，不表示文件已存在：

```text
backend/
├─ teams/
│  ├─ selectors.py       # 列表、详情、本人记录的查询
│  ├─ services.py        # 发布、申请、确认、编辑、离队/解散事务
│  ├─ serializers.py    # 请求字段白名单与公开/本人响应
│  ├─ views.py / urls.py
│  └─ management/commands/settle_team_deadlines.py
├─ notifications/       # 事件收件人生成、本人读取及已读
├─ ingestion/
│  ├─ adapters/         # 每个来源的列表发现、正文提取
│  ├─ services.py       # 版本去重、候选校验、受控采纳
│  └─ management/commands/sync_competitions.py
├─ competitions/        # 统一赛事写入、公开查询
└─ ai_services/         # 仅接受已取得的正文，返回候选结果
```

先按上述职责补最少文件。单文件变大后再拆分，不预先建立大量空目录。前端不直接访问数据库、SMTP 或模型服务。

## 4. 赛事与首页

首页近期赛事直接使用现有列表返回的前若干条，沿用当前最新发布排序。后续如增加“可招募”等筛选，必须落在后端查询中，与分页共同执行；不在前端仅过滤第一页来冒充完整筛选。

赛事中心保留现有名称/主办方搜索、分类参数及分页；范围、标签和“可招募”筛选属于后续按需要补充的功能。分类和标签从管理词表取得，不能硬编码截图中的栏目名称。列表仍使用 `{count, next, previous, results}`，不改现有响应封装。

赛事详情按已有字段展示简介、赛道、参赛资格、人数限制、报名方式、校内安排、各类截止时间和已核验来源。未知日期保持未知；不能从招募开关推导“官方正在报名”，也不能从报名截止推导完整比赛起止时间。

截图中的奖项设置、完整赛程、适合人群没有一一对应的专用结构化字段。确有官方依据时先放入现有详情/赛道/资格文本；不要直接新增一套奖项、日程或 AI 人群画像表。讨论区、站内正式报名、参赛成绩及“我的参赛记录”不在本轮范围。

## 5. 组队业务

### 5.1 固定模板

| 页面内容 | 后端取值与校验 |
| --- | --- |
| 关联赛事 | 必须选择已收录的具体届次，并检查当前允许招募；不能只传任意赛事名称 |
| 标题 | 用赛事标题、所需角色与稳定卡片编号组合展示；不新增自由填写的队名、项目名或项目简介 |
| 已有成员数、计划招募人数 | 分别使用 `existing_member_count`、`recruitment_quota`；已有成员数包括招募者本人；遵守官方已知人数上限 |
| 当前能力、所需角色/技能 | 使用管理员维护的 `RecruitmentOption` 多选；选填；停用项不供新选但保留历史 |
| 基础要求、每周投入、协作方式 | 现有固定单选，必填；线下/混合方式须选校区，纯线上不保存校区 |
| 合作目标、预计合作时长 | 现有固定单选，选填；合作时长与卡片有效期不同 |
| 有效期 | 只选 3/7/14 天；真实到期取所选期限与赛事招募截止较早者，由后端计算并返回 |
| 联系方式 | 不填写到卡片正文、不出现在公开 JSON；通过受权接口读取用户当前资料 |

不照搬截图的“其他要求”自由文本。角色技能不足时由管理员维护词库，不让学生通过自由文本绕过固定模板。发布预览和最终保存都展示后端计算的真实截止时间；保存时必须再次核对。

### 5.2 动作与状态

| 动作 | 处理结果 |
| --- | --- |
| 发布招募 | 同事务创建队伍（首次时）、招募者正式成员关系、卡片和初始版本；同队最多一张处于有效期内且未关闭的公开卡，满员仍占位置 |
| 提交申请 | 创建 `pending` 及申请资料版本；同人同卡仅申请一次；撤回/拒绝后不能向同一卡重申 |
| 招募者接受 | 进入 `contact_open`，双方获得联系方式；此时不占招募名额 |
| 双方确认 | 每方确认当前申请资料版本；第二方确认成功时才创建成员关系、占名额、将申请设为 `joined` |
| 编辑招募 | 实际内容变化创建新版本并保存差异；通知有效申请人及正式平台成员；未完成申请挂起，旧确认不能沿用 |
| 继续申请 | 申请人接受最新卡片版本，可调整本次角色/技能/投入；建立新申请版本，双方重新确认 |
| 撤回/拒绝/结束 | 转入相应终结状态，隐藏对应未入队联系权限；不删除历史、不恢复已结束申请 |
| 退出/移除 | 同一成员关系至多一项待处理请求；对方同意或固定 24 小时未回应后完成；明确拒绝保留关系，本次结束 |
| 解散 | 仅招募者发起；等待中暂停新申请、入队和卡片编辑；其他平台正式成员全同意，或 24 小时届满无人拒绝后完成；任一明确拒绝取消本次 |

“挂起”由申请接受的卡片版本和待处理解散状态计算，不另塞入 `Application.status`。阅读消息不等于接受新条件。卡片编辑不续期，成员入队/离队导致的自动人数变化也不算编辑。

招募者的队伍身份是平台招募发起人，不强行对应现实队长。公开卡片不列出完整成员或其联系资料；“已入队”“我发起的招募”放在本人页面，不能做成全站人员目录。

### 5.3 事务与并发

所有写入口（API、Admin、管理命令、采集联动）调用统一业务服务。保持已有字段文档的锁顺序：**受影响用户按 ID → 赛事 → 队伍按 ID → 卡片 → 申请 → 成员/请求**，各层涉及多行时按 ID 排序。

每次操作使用同一个 `now`，先在锁内结算到期卡片与请求，再检查权限和动作。不能依赖定时任务恰好按时运行来释放卡位，也不能在调用网页或模型时持有这些业务锁。

确认入队时重新检查：账号状态、双方当前确认、最新卡片版本、队伍未解散、赛事仍可招募、卡片未到期、剩余名额、同届唯一有效成员关系。锁住卡片后计数，数据库唯一约束兜底；唯一冲突整体回滚并返回明确业务冲突，不保留半份成员关系。

同用户正式加入一队后，结束其同届其他未完成申请。先列齐受影响队伍并按统一顺序加锁，锁内再次核对；不得先锁申请再逆向锁用户/队伍。编辑名额、入队、离队、解散与赛事停止招募共用同一锁约定。

业务状态、`BusinessEvent`、完整收件人的 `Notification` 在同一事务保存。重复提交已完成的确认/已读等动作返回现状，不重复占位、建成员或发送通知。版本过旧返回冲突并要求前端刷新，不静默覆盖。

当前 `withdraw_competition` 会拒绝下架已有队伍的赛事，这是尚未实现联动时的保护。接通组队前须补统一下架/停止招募服务：结束未入队申请、关闭招募并隐藏相应联系权限，保留正式成员历史及仍有效的成员联系权限。不能简单移除保护或只修改赛事开关。

## 6. 接口安排

### 6.1 保持现有接口

| 接口 | 当前用途 |
| --- | --- |
| `GET /api/v1/competitions/`、`GET /api/v1/competitions/<id>/` | 已发布赛事列表、详情 |
| `GET /api/v1/accounts/csrf/` | CSRF Cookie 与令牌 |
| `GET/PATCH /api/v1/accounts/me/` | 本人资料及联系方式；不能修改验证和权限字段 |
| `/api/auth/browser/v1/...` | 现有注册、登录、验证、退出，具体方法和路径以 API 说明为准 |

普通业务接口末尾保留 `/`；现有 allauth 路径末尾不加 `/`。不修改已有认证响应格式。前端继续通过同源 `/api` 代理，写请求使用 Session Cookie 和当前 CSRF 令牌。

### 6.2 拟新增接口

**下表是接口草案，没有可调用承诺。**实现一个接口后，再把准确字段、权限、错误和样例更新到 `docs/api.md`。动作路径中的大括号表示候选动作集合，不是一个字面 URL。

| 阶段 | 拟方法与路径 | 边界 |
| --- | --- | --- |
| M1 | `GET /api/v1/competitions/options/` | 分类、标签、范围词表；先注册具体路径，避免被详情 ID 路由误匹配 |
| M1 | `GET /api/v1/recruitments/options/` | 角色、技能、校区、固定枚举与天数；返回稳定 code/名称 |
| M1 | `GET /api/v1/recruitments/`、`GET /api/v1/recruitments/<id>/` | 公开招募；拟支持赛事、角色、技能、协作方式、校区、可申请筛选；只搜索已有赛事名称/编码，不承诺不存在的队名搜索 |
| M1 | `POST /api/v1/recruitments/` | 新队首卡或本队新轮次；后端验证所属队与唯一卡位 |
| M1 | `PATCH /api/v1/recruitments/<id>/`、`POST .../<id>/close/` | 仅招募者编辑/关闭；提交看到的版本号防止旧页面覆盖 |
| M1 | `POST /api/v1/recruitments/<id>/applications/` | 提交固定申请资料；意向角色/技能选填，投入必填；提示接受后互见联系方式 |
| M1 | `GET /api/v1/applications/` | 按本人“发出的/收到的”读取；服务端限定申请人或招募者，不能靠请求传来的 user ID 授权 |
| M1 | `POST /api/v1/applications/<id>/{accept,reject,withdraw,end,continue,confirm,revoke-confirmation}/` | 各动作只开放给对应当事人，并检查当前版本与状态 |
| M1 | `GET /api/v1/applications/<id>/contact/` | 只有当前获授权的双方可读对方最新联系资料；禁止缓存，关系失效即不再返回 |
| M1 | `GET /api/v1/teams/mine/`、`GET /api/v1/teams/<id>/` | 本人的队伍、招募、成员与待办；非成员不能读取内部信息 |
| M1 | `POST /api/v1/memberships/<id>/departure-requests/` | 按本人退出或招募者移除创建请求 |
| M1 | `POST /api/v1/departure-requests/<id>/{respond,withdraw}/` | 回应或撤回；校验 24 小时边界与操作者 |
| M1 | `POST /api/v1/teams/<id>/dissolution-requests/`、`POST /api/v1/dissolution-requests/<id>/{respond,withdraw}/` | 解散与回应；无其他平台成员时由招募者明确确认后直接完成 |
| M1 | `GET /api/v1/notifications/`、`POST /api/v1/notifications/<id>/read/` | 本人系统消息、分页和未读筛选；已读动作不能触发接受条件或入队 |
| M2 | `GET /api/v1/research/`、`GET /api/v1/research/<id>/` | 已发布科研机会及原文；不接入参赛组队流程 |
| M2 | `GET /api/v1/newsletters/`、`GET /api/v1/newsletters/<id>/` | 管理员确认发布的快讯版本和来源 |
| M2 | `GET /api/v1/resources/`、`GET /api/v1/resources/<id>/` | 管理员维护的已发布外链资源 |
| M2 | `GET/POST /api/v1/favorites/`、`DELETE /api/v1/favorites/<id>/` | 本人收藏；仅赛事/科研/资源；重复收藏不重复建记录 |

新公开响应用字段白名单。广场返回当前内容版本、有效期、人数计算和可申请状态；本人页面可追加当前用户允许的动作及不可操作原因。按钮状态只是提示，后端每次写入重验。公开/私人 Serializer 分开，不能先返回全部字段再由前端隐藏。

新增接口拟采用：字段不合法 `400`，没有操作权限 `403`，不存在或不应暴露的对象 `404`，版本变化/已满员等业务冲突 `409`，限流 `429`。保留现有端点的既有行为；新接口返回稳定错误 code、中文说明和必要字段错误，禁止暴露 SQL、堆栈或联系资料。

## 7. 持续采集

### 7.1 执行流程

```text
系统每 6 小时 / 管理员手动运行命令
  → 读取启用的 SourceConfig
  → 官方列表发现文章 + 复查仍有效赛事的来源页
  → FetchRun 记录结果
  → 正文规范化、SourceVersion 原文版本去重
  → 规则提取，必要时调用 AI 辅助
  → ProcessingResult 候选、依据、缺项与错误
  → 管理员确认 / 已验证规则采纳
  → 统一赛事事务服务
  → 浏览器以后读取数据库中的已发布内容
```

浏览列表、打开详情和首页不执行抓取或模型调用。公开内容更新失败时仍保留上一份已核验内容，不能用失败、空正文或模型猜测覆盖。

首批只接 2～3 个白名单官方来源。先实际核对页面、允许的访问方式、字段质量，再登记并启用，不在方案中把未测试的网站写成已接入。优先官方接口/订阅或结构稳定通知页；公众号沿用能协调的同步方式，不做绕过登录或反爬的方案。

每个适配器只负责该来源的列表、正文和日期提取；通用服务负责版本、去重和业务写入。遇到来源版式变化、动态脚本页面或 PDF 无法可靠解析，产生待处理记录，不强行生成赛事。

### 7.2 去重、变更和发布

| 情况 | 处理方式 |
| --- | --- |
| 同页正文没变化 | 复用 `(source, source_url, content_hash)` 原文版本，更新最后见到时间，记录 unchanged；不重复生成已处理候选 |
| 同页有变化 | 建新不可变原文版本，保留旧依据，再做字段差异；不覆盖历史 |
| 同届赛事被多个来源报道 | 通过稳定赛事编码、已确认来源映射及届次核对；确定后追加/更新来源；仅标题近似时交管理员确认 |
| 同名不同年份/届次 | 独立赛事对象；不可按同名自动合并 |
| 关键字段缺失或冲突 | 进入候选待处理；未知日期保留空；招募未核验时保持关闭 |
| 新赛事满足条件 | 初期由管理员核对后发布；某适配器经过样本验收后，才可用记录版本号的受控规则自动采纳 |
| 已发布赛事变更 | 先比较候选，不自动覆盖人工更正；日期、人数上限、来源与招募状态等变化须复核或经过专门验证的规则 |
| 页面暂不可达 | 限次重试并记录故障；不据此宣布赛事取消、关闭团队或删除历史 |

采纳候选与正式业务写入在同一短事务完成，重复处理已采纳候选返回原业务对象。相同原文的并发处理通过来源级互斥、锁内复查和已有唯一约束防重；不能把“新增成功后再标记候选”拆成可能重复发布的两步。

赛事 `published_at` 是首次公开时间，`updated_at` 是实际内容更新时间，来源发布日期来自原文，抓取时间是 `fetched_at`。仅重新获取或核验不把旧赛事排成新发布。页面清楚展示来源与核验时间，避免“最新”标签掩盖过期数据。

当前赛事来源编辑服务要求先下架，不能让采集程序通过“临时下架再上线”改来源，这会误伤队伍。初期将此类变更留给管理员；正式支持在线更新前，补一个锁内替换来源、核验最终来源集合且保留公开状态的专用入口。赛事真正下架/停止招募则必须触发第 5 节组队联动。

### 7.3 调度与故障

- 新增 `sync_competitions` 管理命令；按来源选择、手动/定时标记和操作者记录运行。`FetchRun` 是一次实际页面获取，不是任务排队表，不向其现有枚举硬塞 `queued`。
- Windows 任务计划每 6 小时执行一次；Linux 部署使用等效 timer。初期每次串行处理有限页面，设置连接/读取超时、大小限制、来源间隔和有限重试；同来源并行触发时跳过或返回运行中，进程异常退出后能够释放互斥。
- URL 仅允许配置的官方域名和合法 HTTP(S)，逐跳检查重定向，不抓取本机、内网或云元数据地址；用户不能提交任意 URL 让服务器访问。采集原文当作不可信数据，不执行其中指令或 HTML。
- 记录成功/失败时间、状态码和脱敏错误，不记录密钥。连续失败进入管理员可见列表；不向全体用户发故障通知。
- 管理员初期通过命令行手动触发。未来增加 Admin“立即同步”按钮时，必须快速提交后台任务并返回运行标识；确认队列及工作进程后再实现，不能让 HTTP 请求等待全部抓取和 AI 完成。
- 另外新增 `settle_team_deadlines` 定期结算招募到期及 24 小时请求；它与采集周期分开，用户写入口也会即时结算，保证不靠任务准点决定权限。
- 本机调度只有电脑开机且运行环境可用时才执行。连续无人值守采集仍需持续运行的学校机器或后续部署资源。

## 8. 资讯、资源与 AI

创享资讯先提供“科研机会”“俱乐部快讯”两个明确子类。科研保留基本信息、招募主体、官方链接与原文说明，不强制补全不存在的结构化字段。快讯由管理员按需生成草稿并确认发布，不设固定周期；保留已发布版本及引用依据。截图里的泛新闻、人物专访、成果展示和学生投稿不扩建成新闻 CMS。

资源中心复用 `Resource`，首版管理员维护合法外链，暂不增加用户文件上传。收藏仅支持现有 `Favorite` 的赛事、科研、资源三种目标；截图里的招募卡收藏、快讯收藏需要另行明确数据结构，当前不做。

AI 有两种不同用途：

1. **后台通知提取与快讯草稿：**复用现有内部函数；调用方先取得正文或筛选有效输入，再生成候选。保存原文依据、缺项、校验错误、模型/提示词版本和调用结果；AI 不直接发布、改人数或更改权限。关闭或调用失败时仍可规则解析和人工处理。
2. **M3 只读智能助手：**先用 PostgreSQL 对已公开、已核验资料检索，把命中文本交给模型生成附来源的解释。没有依据时明确无相关信息；不查联系方式、内部申请或未发布候选，不代用户报名/入队。历史内容下架后不再作为可公开回答依据。

M3 实现前须单独确定请求限流、费用上限、回答长度、引用校验及超时降级。先离线比较候选模型的字段准确性、缺失值处理、引用真实性、耗时和成本；不以截图为由选定某个型号，也不先加入向量库。智能助手没有通过验收前，前端隐藏入口而不是提供假聊天。

## 9. 分工与验收

| 里程碑 | 后端负责人 | 前端配合 | 数据库配合 | 完成判据 |
| --- | --- | --- | --- | --- |
| M1-A 读与发 | 词表/广场查询、固定模板发布和编辑服务、公开/私有响应 | 广场、详情、表单、实际有效期提示 | 核对字段、版本与人数约束 | 游客能读公开卡且拿不到联系字段；测试账号能关联已收录测试赛事的具体届次发布；旧版本提交不覆盖新内容 |
| M1-B 完整组队 | 申请、授权、确认、通知、离队/解散、到期结算和赛事联动 | 我的组队、待办、继续/撤回、双方确认及通知详情 | PostgreSQL 并发和历史不变性检查 | 两个请求争最后名额仅一人入队；同人同届不跨队；编辑挂起不自动入队；24 小时边界/拒绝/解散联动正确 |
| M1-C 赛事同步 | 先接 1 个来源，再扩至 2～3 个；候选、去重、采纳与系统调度 | 展示来源、更新时间、未知值和空态 | 原文/候选幂等、短事务、采纳与正式记录一致性 | 重复运行无重复赛事；变化保存新版本；失败不抹内容；列表请求不触发抓取；断开 AI 仍可运行规则路径 |

M1-B 的并发、权限、期限和联动验收未通过前，不向真实用户开放发布和申请。M1-C 可与 M1-B 并行开发，但不得把未经核验的采集结果用于真实招募。现有本机演示数据始终保留“虚构样例”标识，不能拿来证明赛事覆盖量或采集成功。

每个里程碑交付可运行接口、文档样例、相关测试和团队进度更新。前端用同一份接口样例开发；数据库同学参与规则与查询检查，不另写一套重复建表 SQL。上线资源和真实发信仍按 [部署说明](deployment.md) 单独验收。
