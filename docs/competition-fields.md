# 赛事字段说明

版本：v1.0，2026-09-24。配套的 [赛事字段表](competition-fields-table.md) 是字段名、类型、长度、空值、默认值与关联的完整清单。用户已通过赛事部分审核；本文将大纲整理为可供建模和接口对齐的交付基线。新增的具体技术取值是落地方案，不表示后端已经审阅或业务已经实现。

## 一 依据、范围与实施阶段

依据用户已审核的赛事设计范围、《创享科创信息与组队服务平台建设方案》《创享平台功能细则补充稿》《数据库开发交付要求》以及仓库 [产品范围](product-scope.md)。规则冲突时沿用较新的补充稿：学生自主组队只用于参赛，必须指向已收录的具体赛事届次。

第一轮建立赛事信息及其来源、分类标签，使后端可以维护和读取赛事列表。本文也确定与后续组队的关联边界；实际队伍、招募、申请、成员关系、收藏及快讯引用模型仍按各自阶段交付。科研项目不包含在本次赛事定稿中。

| 对象 | 一条记录的含义 | 与赛事的关系 |
| --- | --- | --- |
| `Competition` | 一个具体赛事届次 | 赛事主体；后续业务关联这个主键 |
| `CompetitionSource` | 这个届次的一条官方或正式校内来源 | 赛事一对多来源，发布时恰好一个主来源 |
| `CompetitionTaxonomy` | 一个受控的分类或标签词条 | 每届一个主分类、零到多个标签；草稿分类可空 |
| 标签中间表 | 一届赛事与一个标签的关联 | 多对多关系，由 Django 管理 |

同一个年度存在春季、秋季两次独立参赛周期时，可分别设届次；同届不同赛道不另建赛事。首版没有独立的赛事系列表：未来需要跨届聚合页面时再增加系列模型，同时保留既有届次主键及业务关系。

## 二 身份、赛道与重复数据

### 届次是业务关联单位

`title` 用于展示，`edition` 明示年度或届次，`code` 是稳定的内部导入标识。例如虚构赛事可用 `demo-robotics-2026`，展示名为“2026 年演示机器人挑战赛”。名称修改或报名延期时更新同一条记录；下一届创建新记录。

`code` 由建档流程指定，不能每次导入随机变化，也不能由会变动的标题自动重算。相同 `code` 重复导入应更新原记录并保留主键。唯一编码只能防止重复编码，不能自动识别两个不同编码实际属于同届赛事；录入或导入前仍需结合正式名称、主办方、届次和来源核对。发现碰撞时先停止覆盖，确认身份。

标题不能唯一，同一原文 URL 也不能作为全局赛事身份：一篇校内通知可能列出多项赛事，而一届赛事可能同时有官网公告、校内选拔和延期通知。

### 赛道的首版处理

同届赛道写入 `tracks`，具体差异写入 `description`、`eligibility` 和 `deadline_notes`。只有各赛道确实共用的截止时间、团队人数和报名入口才填入主表的结构化字段。不能擅自取最早或最晚截止时间冒充全届统一截止。

如果后续需要按赛道筛选、自动计算分赛道招募资格，再增加归属于同一 `Competition` 的赛道表。届时同用户同届只能正式加入一个队伍的约束仍以届次主键判断。

## 三 公开内容与官方要求

### 列表、详情及词条

- 列表主要读取名称、届次、简介、分类标签、赛事范围、各类截止日期、主来源及平台更新时间。
- 详情补充主办方、官方参赛资格、赛道差异、报名方式、作品提交要求、校内安排及所有已核验来源。
- `summary` 是简短介绍，`description` 是整理后的可阅读详情，两者均为纯文本。展示端按文本转义；首版不把 HTML 或任意富文本写入内容字段。
- 分类与标签由有权限的管理员维护；学生不能自行造标签。主分类只选一个，标签可多选。词条名称可调整，稳定编码与用途固定；停用后保留历史展示，阻止新增选择。
- `level` 仅记录来源明确的赛事范围。未注明填 `unknown`；不根据主办方名气推测“国家级”，也不代表同济认定等级。

词库属于运营数据，不把尚未审核的具体分类名称写成不可调整的数据库枚举。分类名与标签名不重复录入各条赛事；字段类型、词条结构和选择规则在本版固定。

### 团队人数不是招募人数

`team_size_min`、`team_size_max` 只表示官方要求的参赛团队人数，均包含官方规定应计入的成员。未说明时用 NULL，不用 0；如果某赛道特殊，写明范围，不拼成误导性的全届上下限。

`participation_type=individual` 时两个团队人数字段为空且不能开放站内团队招募；`unknown` 不推断为团队赛。`both` 表示同届包含个人和团队参赛形式，并不允许个人赛参加者发布团队招募。

学生队伍现有人数、已线下确定的成员、待招人数、技能要求、投入时间、地点和目标均属于后续 `Team` 或 `Recruitment`，不放入赛事主表。官方报名入口不等于站内入队入口；站内确认入队也不代表报名成功。

## 四 日期、精确时刻和未知信息

### 三类截止事项独立保存

| 事项 | 日期字段 | 精确时刻字段 | 来源时区字段 |
| --- | --- | --- | --- |
| 官方报名 | `registration_deadline` | `registration_deadline_at` | `registration_deadline_timezone` |
| 作品提交 | `submission_deadline` | `submission_deadline_at` | `submission_deadline_timezone` |
| 同济校内报名或选拔 | `campus_deadline` | `campus_deadline_at` | `campus_deadline_timezone` |

`campus_arrangements` 必须解释校内截止具体针对什么事项、适用哪些院系或赛道。存在多个不同校内截止时，主表不强行选一个，完整保存于说明；将来需要自动处理时再拆独立时间节点表。

| 来源实际写法 | 保存与展示规则 |
| --- | --- |
| 没有给出日期，或仅“另行通知” | 日期、精确时刻为 NULL，时区为 `''`；展示“时间待通知/未提供” |
| 只写“2026 年 10 月 15 日截止” | 只填日期；不补午夜或当日最后一秒；明确展示“具体时刻未注明” |
| 写明“2026 年 10 月 15 日 18:00，北京时间” | 日期为 `2026-10-15`，保存对应带时区时刻，时区为 `Asia/Shanghai` |
| 写了时间但没有可确认的时区 | 保留完整原文信息于 `deadline_notes`，精确时刻留空；核实时区后再补齐 |
| 仅“10 月 15 日”，年份也无法从原文明示的上下文确认 | 不拼接当前年份；留空并记录待核验信息 |
| 不同赛道截止不同、分批报名或分阶段提交 | 在说明中分别保留；只有确属全届统一节点才填公共字段 |

精确时刻保存为带时区的时间点，按来源时区转换得到的日期必须与对应 `DateField` 一致。时区填写可解析的 IANA 名称或固定 UTC 偏移，不用含义不唯一的缩写。只有日期而来源明确时区时，可以保留时区；不知道则留空，不能把界面展示时区当作来源事实。

日期与精确时刻同时存储的目的是保留来源精度；所有写入路径必须一次校验并更新配套字段，避免改了日期而遗漏旧时刻。时间配套空值关系可以做数据库检查，时区解析与本地日期一致性由统一写入校验处理。

### 状态和排序

- 日期为空是未知，不等于长期有效，也不能推断已经结束。
- 有精确时刻时可准确判断该节点“未截止/已截止”；只有日期时只显示“日期未到/今日截止日期/截止日期已过”，附“具体时刻未注明”。日期比较使用已知来源时区；未知时以页面北京时间作日历提示，不能据此开放招募。
- 截止尚未到不能单独证明“报名已开始”，因为首版没有统一报名开始时间；不输出没有依据的“报名中”状态。
- 最近发布按平台 `published_at` 降序、主键降序排列；临近报名截止视图排除已明确截止的记录，再按 `registration_deadline` 升序、空日期放最后、主键作稳定次序。已截止记录仍可通过公开历史查询。作品提交或校内截止使用各自筛选/排序，不混成一个不标事项的时间。
- 不硬性规定报名截止早于作品提交截止或校内截止早于官方截止；不同赛事可能有例外，异常提示核验即可。
- 当前 AI 提取仅提供 `YYYY-MM-DD` 日期和原文依据，可对齐两个日期字段；它不能提供或推算本方案的精确截止时刻，也不直接写库或发布。

## 五 来源、更新时间与发布校验

### 来源分别保存

`CompetitionSource` 保存赛事官方及校内官方通知。每届最多一个 `is_primary=True`，发布时必须恰好一个。第一条来源建立后由写入流程明确设为主来源；切换时使用事务，先取消旧主来源再设新主来源。公开赛事更换主来源时必须在同一事务内完成最终校验。

同一赛事下重复的原文链接由导入流程规范化、匹配并更新已有来源；写入时锁定所属赛事，避免并发导入重复来源。规范化不能随意删除有意义的查询参数。来源链接不设置全局唯一；不同届次可以引用同一原文。发布校验要求公开返回的来源都已核验、确实适用于本届；未核验候选链接留在后续采集处理区，不作为正式公开来源。

原始发布日期和原文更新日期首版按日保存，字段名明确用 `_on`。不知道原始发布日期就留空，不用平台时间顶替；现阶段不为来源时间强加不存在的秒级精度。后续确需精确来源时间时，再增加精度明确的字段。

| 时间 | 含义 | 不能替代什么 |
| --- | --- | --- |
| `source_published_on` | 原通知发布日期 | 不等于平台发布或抓取日期 |
| `source_updated_on` | 原文明确的更新日期 | 不能用重新采集日期刷新 |
| 来源 `fetched_at` | 最近成功读取来源的时间 | 不代表人工核验，也不代表原文有更新 |
| 来源 `last_verified_at` | 此来源内容最近核验时间 | 不自动代表整届所有信息已核验 |
| 赛事 `last_verified_at` | 本条赛事整合信息最近核验时间 | 单纯保存、读取、重抓或 AI 生成不能刷新 |
| `created_at` / `updated_at` | 平台建档 / 内容修改时间 | 不能宣称是原通知发布时间 |
| `published_at` | 平台首次对公众发布的时间 | 更正、重新上架和原样导入不重置 |

源链接、时间、资格或报名信息变更时必须重新核验受影响部分并确认整条赛事的一致性；确认后再公开更正。未来自动化校验流程需要保留可追溯结果，不能仅让 AI 填一个时间就视为通过。

### 发布所需信息

草稿只强制有稳定编码、标题和可识别的实际届次，其他字段按表中默认值建档。尚不能识别届次的原始材料属于待整理输入，不先伪造赛事届次。

从草稿发布或下架后重新上架时，统一校验以下内容；修改公开记录也适用，不能通过 Admin、导入脚本或批量更新绕开：

1. 标题、届次、简介和详情非空，内容能识别该届赛事；首次或重新发布时主分类为启用的分类词条。公开记录的一般更正可保留既有停用关联，但不能新增选择停用词条。
2. 恰好一个主来源；所有公开来源名称和 URL 合法，并有核验时间；整条赛事也有核验时间。校内安排须有支持其内容的校内来源。
3. 数字、枚举、文本长度、词条用途、日期和精确时刻配套关系全部合法。
4. 缺失资格、人数或截止日期保持未知并在页面说明，不因个别非核心字段缺失而猜填，也不因此一律禁止发布。
5. 如果同时启用平台招募，额外通过下一节的招募条件校验。

词条停用只阻止新增选择，不立即隐藏历史赛事；既有公开内容继续展示原词条。后续重新发布时更换为启用词条。

### 发布状态

| 当前状态或操作 | 处理规则 |
| --- | --- |
| `draft` | 仅授权维护人员可见；`published_at` 为空 |
| 首次发布为 `published` | 核验通过，在同一事务内写入首次发布时间 |
| `published` 内容更正 | 保留首次发布时间；核验更正内容并更新内容更新时间 |
| 从 `published` 下架为 `withdrawn` | 必填内部下架原因，并关闭招募开关；公共列表与详情停止返回；既有队伍和成员关系保留 |
| `withdrawn` 重新发布 | 重新通过发布校验；保留首次发布时间与最近一次下架原因，原因仍不公开 |
| 报名或作品提交截止经过 | 不自动改为草稿或下架；仍可作为公开历史被检索 |

首版不增加独立的 `archived` 发布状态，不支持将已发布过的记录退回从未发布的草稿。下架记录必须有曾经发布的时间；首次发布前的弃用草稿保持草稿或按删除条件处理。`withdrawal_reason` 只记最近一次原因，完整状态历史留给后续操作日志，不能把这个字段宣称为完整审计记录。

公开返回由服务端以 `publication_status=published` 过滤；草稿和下架的详情请求同样不得泄露内容。`code`、维护人、下架原因、招募核验说明、采集时间等内部字段不进入公开字段白名单。

## 六 与队伍和招募卡的衔接

赛事决定这一届的官方条件和站内招募上限；学生队伍及卡片表达具体团队的需求。建议后续使用以下唯一关联路径，避免冗余字段不一致：

| 后续对象 | 关联方式与职责 |
| --- | --- |
| `Team` 队伍 | `competition` 外键关联本届 `Competition`，使用 `PROTECT`；保存队伍及成员规模，正式关联后不随意换届 |
| `Recruitment` 招募卡 | 外键关联 `Team`，经队伍取得赛事届次；保存岗位、要求、名额、卡片期限；同队最多一张有效卡 |
| `Application` / 成员关系 | 关联具体招募或队伍；同用户同届只能正式加入一个队伍，由后续成员模型及入队事务保证 |
| 收藏 / 快讯引用 | 关联届次主键；记录过期或下架不能造成悬空引用，具体保留和展示规则在对应模块确定 |

### 赛事侧开放招募的条件

赛事创建时 `recruitment_enabled=False`、`recruitment_deadline=NULL`。管理员启用前需确认：

1. 赛事处于公开状态，官方允许相应团队参赛，`participation_type` 为 `team` 或 `both`。
2. 已明确可以组队的适用范围和期限，填写带时区的 `recruitment_deadline` 及内部 `recruitment_note`；启用时期限必须晚于当前时间。来源只给了日期或时区不清时，先核实或确认一个有依据的、更早的平台停止招募时刻，不能把日期自动补到 23:59:59。
3. 平台期限不晚于适用于这些队伍的官方组队、报名或校内选拔限制。不是机械取所有日期中的最小值，也不把作品提交截止当作当然可以组队到该时刻的依据。
4. 涉及多个赛道且还不能结构化判定各自资格时，只在能核实全届统一开放条件与期限时启用；否则保持关闭，赛事仍可公开浏览。

进入组队阶段后，新卡片采用方案约定的 3、7、14 天期限，实际有效期不能超过赛事侧期限；临近赛事期限时如何展示可选时长，在招募卡字段和交互中一并落定。

是否现在允许招募应实时结合发布状态、开关、截止时刻和用户的邮箱验证、联系方式、限制状态判断。赛事下架、关停招募或超过平台招募截止时刻后，即使旧卡片还留在数据库，也必须停止新发卡和新申请；保留已正式加入的成员、已有成员联系权限和退出处理。已有申请能否继续接受、确认入队以及相应联系权限何时终止，留到申请与成员字段表集中确定。既有队伍不因招募卡过期而消失。

本节确定关联边界和赛事侧条件，不冒充已完成 `Team`、`Recruitment` 或申请字段表；它们仍需按此前方式单独整理和审核。

## 七 约束放在哪一层

数据库约束负责底线，统一写入流程负责跨表与业务校验。Django `save()` 本身不会自动执行完整模型校验，不能只写字段说明或 `clean()` 就认为所有入口都已受保护。

| 层级 | 应落实的规则 |
| --- | --- |
| 数据库唯一约束 | 赛事 `code` 唯一；词条 `code` 唯一；同用途词条名称唯一；每届至多一个主来源的条件唯一约束；标签中间表的赛事与词条组合唯一 |
| 数据库检查约束 | 枚举取值合法；必填字符串去空白后非空；编码格式；人数为空或至少 1，最小人数不大于最大人数；个人赛团队人数为空且不开招募；日期与精确时刻、时区的基本空值配套；草稿无发布时间，公开或下架状态有发布时间；下架原因非空；启用招募时必须已公开、形式合法且期限和说明齐全 |
| 模型及统一服务校验 | 文本长度及 URL 协议；时区解析、精确时刻与来源日期一致；词条用途；发布前分类和来源核验；跨来源的信息一致；招募期限依据；首次发布时间及固定编码不可被随意改写 |
| 事务和并发处理 | 发布/下架及重新发布；主来源切换；按稳定编码导入及来源去重；时间配套修改；后续入队人数与同届唯一队伍校验 |
| 权限与接口 | 仅授权人员维护官方赛事；公众只读公开字段；维护人由服务端确定；不信任客户端传入的审核时间或发布权限 |

发布条件中的“恰好一个主来源”、分类/标签用途等跨表规则不能只靠普通 `CHECK` 约束完成，必须由统一入口在事务结束前验证。发布中的来源和标签修改也要走这个入口。变更数据的导入命令、Admin 和将来的 API 共用规则；不要使用绕过规则的任意 `QuerySet.update()` 或批量写入。

`updated_at` 在主表普通保存时自动更新，但来源和多对多关系的变化不会天然触发主表保存；实现时应由统一写入服务显式更新它。只有抓取时间或核验时间变化、内容没有变化时，限定保存字段，不更新主表 `updated_at`。重复导入内容完全相同的数据保持原样。

索引基线：保留主键、外键和唯一约束产生的索引；增加 `(publication_status, published_at, id)` 与 `(publication_status, registration_deadline, id)`，支撑公开列表和报名日期排序。其他索引按实际接口查询增加，不给长 URL 建无依据的索引。

### 删除规则

已发布过或已被队伍、收藏、快讯等业务引用的赛事不硬删除，采用下架保留身份。只有从未发布且无业务引用的草稿可由授权管理员删除，所属来源随之清理；后续业务外键使用保护策略。分类和标签被引用时不硬删除，通过停用管理；标签侧需在删除入口显式检查引用，不能依赖默认多对多级联保留历史。

维护用户被删除时 `created_by`、`updated_by` 置空，赛事不被级联删除；用户禁用不影响已有维护记录。首版这些字段只提供最近维护信息，完整操作追溯由后续日志承担。

## 八 交给后端的边界与下一步验收

字段表确定的是持久化含义，公开接口的 URL、字段组织、来源嵌套方式、分页参数、筛选参数和错误格式仍需在 [API 说明](api.md) 中与实现一同落定。接口用白名单序列化，不能直接返回整张模型表；精确时刻采用带偏移的 ISO 8601，日期采用 `YYYY-MM-DD`，未知值保持 `null`。

按《数据库开发交付要求》的第一轮流程，文档同步后继续：

1. 结合 [用户字段表](user-fields-table.md) 实现 `accounts.User`，配置 `AUTH_USER_MODEL`，再实现本次赛事及辅助模型。
2. 生成并提交相应初始迁移，在新的空开发库验证，避免先迁移默认用户表。
3. 准备明确标记为虚构的分类、标签、已公开赛事、草稿、下架赛事及日期缺失样例；已公开数量超过接口实际页大小，按稳定编码重复导入不重复建档。
4. 检查编码重复、空必填值、人数范围、非法发布状态、多个主来源、日期与时刻不一致等会被拒绝；验证未知日期的已核验赛事可以发布、个人赛不能开团队招募。
5. 后端实现 Admin 与公开列表后，验证草稿和下架详情也不会泄露、已截止公开历史保留、空日期排序正常，并由前端联调。
6. 更新初始化说明、进度和 API 文档，模型、迁移、样例导入及验证结果一并交付。

本轮通过 `database/round1-models` 分支交付赛事字段文档及对应第一轮模型代码，供后端审核和接续；尚未生成初始迁移、在开发库建表或联调，也未合入 `main`。科研项目、队伍及招募卡保持各自待整理状态。

## 九 当前模型实现边界

已实现三张模型及标签多对多关联、字段验证器、数据库约束定义和查询索引；模型 `full_clean()` 检查来源日期与精确时刻一致、主分类用途、发布所需来源和核验字段、首次发布时间与稳定编码等。标签关联的标准 `add` / `set` 入口会拒绝分类和停用标签；被使用的词条与曾经发布的赛事受到删除保护。

赛事模型保留 Django 标准的 `save()` 行为，不隐式执行跨表发布流程。后端需提供统一事务写入入口，在保存前调用 `full_clean()`，并锁定相关记录、管理主来源切换、标签和来源更新时的赛事时间戳、下架开关、首次发布时间及操作者。`objects.create()`、批量更新、直接写标签中间表等都不能替代该入口。真实来源可信度、招募期限依据和权限也由业务流程保证；模型无法从一段核验说明自动判断这些事实。

本轮 31 项新增模型测试与 28 项原有测试均在独立 SQLite 内存库通过；这验证了模型和基础约束，不替代下一步 PostgreSQL 迁移及约束验收。迁移仅执行过 `--dry-run` 预览，未写迁移文件或修改开发数据库。
