# 下一阶段分工

更新日期：2026-09-26。三人继续按前端、后端、数据库主责协作，每轮共同交付一条可操作的业务流程。详细规则见[前端方案](frontend-plan.md)、[后端方案](backend-plan.md)和[产品范围](product-scope.md)。

**执行更新：**下列两轮任务的组队、通知、分类、采集和调度代码已实现并通过 PR #5 合入主分支。真实赛事首次入库、任务安装和现场联调仍按[当前进度](progress.md)逐项验收，下面表格保留原验收目标。

## 制定任务时的基础（历史）

- **已有：**首页、赛事列表与详情、账号页、404 页及统一蓝白界面；赛事查询与管理、账号和本地验证码流程；组队、采集等模型与迁移。新版界面已完成本机检查，12 项前端测试与构建通过，共享状态见[进度表](progress.md)。
- **待做：**组队页面与业务接口、分类和招募词表接口、真实赛事采集、持续调度。已有数据表不等于这些功能已经可用。
- **暂缓：**真实 SMTP 发信、公网部署、资讯资源栏目和 AI 助手。开发继续使用测试账号与控制台验证码，保留身份和权限检查，不绕过核验。

每轮先确认接口样例和字段，再分别开发，最后把页面接到真实后端检查完整流程；这一步就是联调。首页和赛事页作为共同界面基础，前端无需重新设计一遍。

## 第一轮：招募展示与发布、首个采集来源

| 主负责 | 任务 | 依赖与交接 | 完成标准 |
| --- | --- | --- | --- |
| 前端 | 沿用现有布局，增加团队广场、招募详情、固定模板发布页；赛事中心补分类筛选 | 根据后端词表生成选项；对接公开招募查询及发布接口，提前按约定 JSON 样例开发 | 游客可筛选和查看卡片；测试账号可选已收录赛事发布；加载、空结果、无权限和提交失败均有明确提示 |
| 后端 | 实现分类／招募词表、招募列表详情、发布和编辑服务；复用账号门槛，检查赛事届次、人数、唯一有效卡和版本 | 先与数据库同学对齐字段，再给前端接口样例；公开响应不含联系方式 | 发布后刷新仍可见；非法字段和过旧版本被拒绝；同队重复发布被阻止；数据与初始版本同事务保存 |
| 后端 | 接通一个确认可用的官方来源，新增手动采集命令：获取原文、保存版本、提取候选、记录结果 | 数据库同学核对来源与候选关联；使用合法可获取页面，先验证规则解析，AI 可暂不开启 | 同一通知重复采集不产生重复赛事；原文变化保留新版本；缺失字段不猜测；确认后的赛事可通过现有接口展示 |
| 数据库 | 核对现有招募、版本、来源和候选模型；补完整词表、脱敏样例与字段说明 | 重点确认选项 code、必填项、枚举、人数和去重条件；发现缺项才修改模型并生成迁移 | 前后端使用同一套字段与样例；迁移可应用；停用词条保留历史；不另建一套重复表 |

本轮先完成团队内部演示。卡片为预先编写的 Vue 组件，页面读取已保存的数据；浏览时不等待采集或 AI。申请链路未完成前，不向真实用户开放发布和申请。

## 第二轮：完整组队与持续采集

| 主负责 | 任务 | 依赖与交接 | 完成标准 |
| --- | --- | --- | --- |
| 前端 | 增加我的组队、申请处理、联系方式授权展示、双方确认和系统通知；接入撤回、变更后继续、退出／移除等操作 | 使用后端返回的当前状态、允许动作和失败原因；不能仅靠按钮隐藏控制权限 | 两个测试账号走通申请、接受联系、双方确认入队；条件变更后需重新确认，授权失效后不再显示联系方式 |
| 后端 | 实现申请、接受／拒绝、撤回、联系授权、双方确认，以及到期、编辑挂起、退出／移除／解散和赛事变更联动 | 事务服务由后端主写；数据库同学配合锁、约束和历史检查；同步更新状态表与错误码 | 接受申请不占名额，双方确认才入队；争最后一个名额仅一人成功；重复提交不重复入队；越权和旧版本操作被拒绝 |
| 后端 | 扩至 2～3 个可靠来源，增加每 6 小时调度、手动触发、超时重试、运行互斥和异常记录 | 先用 Windows 任务计划运行 Django 命令；机器需持续开机，后续部署再迁移调度 | 重复执行不重复发布；采集失败不清空旧数据；截止等重要变更可追溯；官网发布时间与采集时间分开 |
| 数据库 | 配合验证并发名额、同人同届成员关系、不可变历史和候选采纳一致性；按查询需要检查索引 | 与后端共同跑 PostgreSQL 事务场景；确有模型修改时提交迁移和说明 | 无超员、重复成员或半完成记录；历史版本不被覆盖；队友可在自己的开发库复现关键场景 |

AI 后续优先接入通知字段提取：后端连接现有 `ai_services`，数据库保留候选、原文依据和调用记录，前端只展示已采纳结果。先用样本验证准确性和费用，再决定启用范围。

## 交接要求

1. 每项任务写明负责人、依赖和完成标准。接口先更新 [api.md](api.md)：地址、参数、字段类型、权限、状态、错误码，以及成功／空结果／失败样例。
2. 模型修改者生成并提交迁移；前端不自行改变字段含义，后端不绕过已有约束。样例不包含真实联系方式、验证码或密钥。
3. 合并前共同联调，随后在[进度表](progress.md)记录实现、验证、遗留项和真实提交链接；本机完成、合入主分支与公网可用分别记录。
