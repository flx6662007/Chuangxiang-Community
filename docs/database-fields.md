## 用户与账号

### 已确认的产品规则

| 事项 | 确认结果 |
| --- | --- |
| 注册与登录 | 使用 `@tongji.edu.cn` 学校邮箱及密码；同一邮箱只能对应一个账号，邮箱去首尾空格并统一小写 |
| 公开身份 | 注册时生成类似 `CX-7K2M9Q4R` 的唯一系统代号；每个账号固定使用，用户不能自行修改；公开页面不展示邮箱或其他联系方式 |
| 邮箱绑定 | 首期每个账号绑定一个学校邮箱；验证后不开放自助换绑，特殊情况由管理员处理，新邮箱必须重新验证 |
| 未验证账号 | 可以登录、查看公共内容和自己的账号状态、重发验证码；不能发布招募或提交申请 |
| 邮箱验证状态 | 以 allauth 的邮箱验证记录为唯一来源，不在用户表中维护第二份验证状态 |
| 业务限制 | 新增招募和提交新申请一起限制；每次固定 24 小时，到期自动恢复，管理员可以提前解除 |
| 受限期间 | 保留登录、查看已有记录、申请退出和联系管理员提出异议的能力；已有成员关系继续保留。按 2026-09-25 简化治理要求，不新增独立申诉流程 |
| 联系资料填写 | 注册时保存学校邮箱；首次发布招募或提交申请前，微信号、手机号至少填写一种，允许两种都填，保存到账户并支持后续修改 |
| 联系资料展示 | 发起人接受申请后，仅向具有联系权限的对应另一方展示学校邮箱及已填写的微信号、手机号；申请结束、退出或移除完成后隐藏 |
| 联系资料修改 | 当前仍有联系权限的对象同步看到最新值；不继续展示此前保存的旧版本 |
| 账号关闭 | 首期不提供自助注销，由管理员处理关闭与个人资料处理申请 |

学校邮箱验证仅说明邮箱使用权，页面统一使用“学校邮箱已验证”。手机号目前只是联系资料，首期不新增短信认证或手机号登录。

### 数据归属与实施阶段

本版将账户基础与额外联系资料统一放在 `accounts.User`，不增加一张只有两个联系方式字段的资料表。

| 模型或关系 | 用途 | 实施阶段 |
| --- | --- | --- |
| `accounts.User` | 账号基础、系统代号、微信号和手机号、Django 基础权限 | 第一轮建立；联系方式在注册时可空，发布与申请时的检查随组队功能接入 |
| Django `Group`、`Permission` 及用户的多对多关系 | 学生管理员等后台权限分配 | 保留 Django 机制，具体权限随功能配置 |
| allauth `EmailAddress` | 学校邮箱归属、主邮箱及验证状态 | 后端接入并锁定 allauth 版本时，由其迁移创建 |
| `accounts.UserRestriction` | 记录每次 24 小时业务限制和提前解除 | 已通过 accounts.0002_userrestriction 建表；管理操作与限制去重由后端事务入口接入 |
| 队伍、申请、成员、收藏、管理员操作等模型 | 通过外键关联用户 | 模型已建立，通过具体关系关联用户；事务接口待接入，不存为用户表中的数组或全局角色标签 |

自定义用户继承 `AbstractUser`，移除 `username`、`first_name`、`last_name` 字段，以 `email` 为登录标识；配套自定义用户管理器、后台表单，并将依赖姓名或用户名的显示方法适配为系统代号。首次迁移前设置 `AUTH_USER_MODEL = "accounts.User"`，自定义用户必须在 `accounts` 的首次迁移中创建。参见 [Django 5.2 自定义用户说明](https://docs.djangoproject.com/en/5.2/topics/auth/customizing/)。

### 用户表字段

模型：`accounts.User`；表名沿用 Django 默认的 `accounts_user`。

字段表中的类型、长度和默认值为本版确定值。`NULL` 表示数据库空值；可选字符串统一用空字符串 `''` 表示未填写，不同时使用两种空值。时间使用带时区的时间值，界面按 `Asia/Shanghai` 展示。

字段类型、长度、空值和默认值见[用户字段表](user-fields-table.md)。各字段的写入与可见范围如下。

| 字段 | 写入规则 | 可见范围 |
| --- | --- | --- |
| `id` | 主键；创建后不修改 | 内部关联或必要的接口引用；公开称呼使用系统代号 |
| `email` | `unique=True` 并增加忽略大小写的唯一约束；去首尾空格、全小写；普通用户不能通过资料编辑接口修改 | 本人、授权管理人员；获得联系权限的对应另一方 |
| `password` | 不要求唯一；只能通过 Django 密码处理接口写入，不能直接保存明文 | 所有客户端接口均不返回；管理员也不展示哈希 |
| `public_code` | 唯一；格式为 `CX-` 加 8 位大写字母或数字；碰撞时重新生成；客户端不可指定或修改 | 可随公开招募等业务内容展示；不建立学生资料浏览目录 |
| `wechat_id` | 不设唯一约束；去首尾空白；用户可修改；保存微信号文本，不保存二维码、链接或图片 | 本人、具备处理权限的管理人员、获联系权限的对应另一方 |
| `phone_number` | 不设唯一约束；用字符串保留国家区号；用户可修改；格式校验由前后端统一，不宣称号码归属已验证 | 同 `wechat_id` |
| `contact_updated_at` | 后续微信、手机号变更或学校邮箱换绑成功时更新；用户不可直接提交 | 本人、授权管理人员；不在公开卡片中返回 |
| `is_active` | 由授权管理员处理停用；邮箱未验证或 24 小时业务限制均不改变此字段 | 本人和授权管理人员 |
| `is_staff` | 仅授权管理员设置；仍需配套具体操作权限 | 授权管理人员；必要时用于本人后台入口判断 |
| `is_superuser` | 仅可信的管理员创建和授权流程设置；学生内容管理员不默认开启 | 授权管理人员；不作为公开资料 |
| `date_joined` | 创建后不由普通用户修改 | 本人和授权管理人员 |
| `last_login` | 认证流程维护；不是最后浏览或操作时间 | 本人和授权管理人员 |

密码、权限标记和登录时间沿用 Django 认证字段的职责，具体长度也已核对本机 Django 5.2.17。参见 [Django 用户与权限字段](https://docs.djangoproject.com/en/5.2/ref/contrib/auth/)。

#### 用户组与具体权限

下列关系不存为 `accounts_user` 的普通列，由 Django 管理关联表。

| 关系字段 | 类型 | 默认值与作用 | 谁可修改 |
| --- | --- | --- | --- |
| `groups` | 到 Django `Group` 的多对多关系 | 默认为空；建议用“学生管理员”等组统一分配内容维护、账号管理等权限 | 授权管理员 |
| `user_permissions` | 到 Django `Permission` 的多对多关系 | 默认为空；按需授予特定权限，优先通过用户组维护 | 授权管理员 |

招募者、申请人、成员由具体队伍和申请关系确定；“招募者”不等于现实队伍的队长。同一个用户可以在不同赛事或届次承担不同角色，但同届只能正式加入一队，招募者也受此限制；不新增全局招募者/成员角色字段。（称谓及招募者资格按 2026-09-24 用户确认更新。）

### 学校邮箱验证关联

复用 allauth 的 `EmailAddress`。下表只定义项目需要的含义；实际主键类型、列长度、索引及迁移以最终锁定的 allauth 版本为准，不手工重建或改造第三方表。

| 字段 | 类型或关系 | 项目中的含义 | 写入与读取规则 |
| --- | --- | --- | --- |
| `id` | 第三方模型主键 | 邮箱记录标识 | 由 allauth 管理 |
| `user` | 到自定义用户的外键 | 邮箱属于哪个账号 | 关联 `settings.AUTH_USER_MODEL`；不关联 Django 默认用户表 |
| `email` | 邮箱字符串 | 需要验证的邮箱 | 当前生效的主邮箱应与 `User.email` 一致，并使用同样的规范化规则 |
| `verified` | 布尔值 | 该邮箱是否完成验证 | 新邮箱默认未验证；只有正确的验证流程才能置为 True；不接受客户端直接修改 |
| `primary` | 布尔值 | 是否为当前主邮箱 | 正常状态只有一个当前绑定主邮箱；管理员换绑流程保持一致性 |

项目允许一个当前绑定学校邮箱；allauth 的原生用户与邮箱关系仍可为一对多。管理员换绑所需的临时待验证记录不等于第二个已经生效的绑定邮箱。接入时统一处理 `User.email`、主邮箱标志和验证记录，避免只修改一个字段。

未验证账号允许登录，发布和申请仍必须通过邮箱验证。后端锁定 allauth 版本后按此规则配置并联调验证码、重发和换绑，技术步骤见[邮箱验证接入](backend-development.md#email-integration)。

尚未接入 allauth 时，不创建虚假的已验证状态，也不因当前验证表尚未建立而在 User 中临时加一个验证布尔值。

### 业务限制记录字段

模型：`accounts.UserRestriction`；表名 `accounts_userrestriction`，已完成建表。一个用户可对应多条历史限制记录；当前是否受限由有效记录计算，不在 User 中重复维护 `is_restricted` 或另一份截止时间。

字段清单见[用户字段表的业务限制记录](user-fields-table.md#业务限制记录)。限制原因由管理员填写，只向本人及授权管理员展示；starts_at 使用同一次操作的当前时刻，expires_at 固定为 starts_at 加 24 小时。提前解除时同时写 revoked_at、revoked_by 和非空 revoke_reason，自然到期不写撤销字段。

到用户的多个外键使用 related_name='+' 关闭反向访问，避免命名冲突。所有限制记录只允许目标本人和具备处理权限的管理人员访问；向本人展示原因与时间，不必暴露管理员的私人联系方式。

有效限制的判断规则为：`starts_at <= 当前时间 < expires_at`，且 `revoked_at IS NULL`。到期时判断自然变为不受限，无需等待定时任务修改一个布尔值。提前解除填写撤销字段，不回写或抹掉原定截止时间。

添加 `(user, expires_at)` 查询索引，以及截止时间固定为生效后 24 小时、解除时间与操作人同时有值或同时为空等约束。限制期间重复点击处理同一账号，默认返回当前有效记录，不叠加、不重置 24 小时；事务内锁定目标用户，防止并发重复创建。不叠加与不重置规则由后端在锁定用户的事务入口落实。

### 计算得到的状态

以下可作为账号状态接口的返回值，但不增加同名数据库列。

| 名称 | 数据来源与含义 | 使用范围 |
| --- | --- | --- |
| `school_email_verified` | 当前 `User.email` 对应的 allauth 主邮箱记录已验证，且属于允许域名 | 本人状态、公开卡片上的“学校邮箱已验证”标记、服务端权限检查 |
| `has_contact_details` | 规范化和校验后的微信号、手机号至少有一项已填写 | 本人提示及发布、申请前检查；学校邮箱本身不能代替额外联系资料要求 |
| `is_restricted` | 是否存在本节定义的当前有效限制记录 | 本人状态、管理员处理及服务端权限检查 |
| `restriction_ends_at` | 当前有效限制记录的截止时间；无有效限制时为空 | 本人及授权管理员，不公开 |
| `can_publish`、`can_apply` | 账号层面满足登录、启用、学校邮箱已验证、未受限且联系资料已补齐 | 本人界面提示；实际接口还必须校验赛事、队伍、名额、重复申请等对象和业务规则 |

接口中的验证标记只能由后端计算。发布与申请每次请求都需重新检查，不能仅在用户第一次操作或前端按钮显示时检查。

### 联系资料的读取与修改

1. 注册邮箱保存在 `User.email`，不增加重复的 `contact_email` 字段。
2. 微信和手机号分别保存，允许两项都有；不需要再设置只能二选一的 `contact_type` 或首选渠道。
3. 发布或提交申请前要求微信、手机号至少一项通过格式校验；仅有学校邮箱仍需补充。
4. 发起人接受申请后，仅在发起人与对应申请人之间开放联系资料；正式入队后该对应联系权限保留，其他队友不会自动获得查看所有人联系方式的权限。
5. 有效联系权限下返回当前学校邮箱及已填写的微信、手机号；对空值可不展示，但不能用邮箱前缀替代系统代号。
6. 用户修改资料后，仍有联系权限的对应另一方读取最新值；不把首次解锁时的联系方式复制进申请或成员表作为后续展示来源。
7. 申请撤回或终止、成员退出或移除完成后，不再返回联系方式。招募卡关闭本身不撤销已有成员关系的联系权限。
8. 公开接口使用明确的字段白名单；私有联系资料由检查了当前关系权限的接口返回，不能先给前端再隐藏。

联系资料字段在数据库层允许为空，因为注册时尚未补充；“至少填写一种”属于发布与申请时的条件校验，不添加阻止空资料注册的全表检查约束。

### 约束与校验清单

| 对象 | 数据库层 | 后端输入及业务层 |
| --- | --- | --- |
| 学校邮箱 | 非空、非空字符串；普通唯一约束加 `Lower(email)` 函数唯一约束；建议增加存储值已去首尾空格且为小写的检查 | 全路径使用 `strip().lower()`；校验邮箱格式和精确域名 `tongji.edu.cn`，不能用模糊字符串包含判断；注册、管理命令及换绑都执行 |
| 系统代号 | 非空、唯一、最大长度 11；建议检查 `CX-` 加 8 位大写字母或数字的格式 | 系统随机生成；唯一冲突时有限重试；注册和资料接口禁止传入代号覆盖生成值 |
| 密码 | 使用 Django 内置存储字段，不额外保存原始密码 | 使用 `set_password` 或认证组件的等效安全入口；执行项目密码校验；所有读接口排除密码字段 |
| 微信与手机号 | 允许空字符串、不允许 NULL；各自限制长度；不设唯一约束 | 去除无意义首尾空白，校验格式；发布和申请时至少一项有效；只允许修改自己的资料 |
| 24 小时限制 | 时间与解除字段成对一致；记录关联有效用户和操作者 | 仅有权限的管理员可创建或解除；同一操作中计算开始与到期；每次请求判断是否已到期 |
| 管理权限 | 默认使用 Django 的关联表和布尔字段 | 普通用户不能写入 `is_staff`、`is_superuser`、`groups`、`user_permissions` 或限制记录 |
| 邮箱验证 | 使用 allauth 自带迁移及约束，并保留 User 自身唯一性要求 | 验证状态不可由客户端直接写入；当前生效主邮箱与 User.email 一致；换绑的新邮箱重新验证 |

忽略大小写的唯一性由数据库承担，避免仅靠注册接口规范化而被其他写入路径绕过。Django 支持基于 `Lower` 表达式的唯一约束，见 [Django 约束说明](https://docs.djangoproject.com/en/5.2/ref/models/constraints/)。普通 `email` 唯一约束同时便于其作为 Django 登录标识；不再为已有唯一索引的列重复增加相同普通索引。

### 首版边界处理

本节处理方式随用户对字段表的整体确认一并纳入 v1.0。认证接口和账号关闭流程的实现细节在对应阶段与后端集中对齐，不阻塞用户基础模型。

| 场景 | 首版处理方式 |
| --- | --- |
| 未验证邮箱再次注册 | 不创建第二个账号，不覆盖已有账号密码或资料；引导走登录、验证重发或密码找回流程，具体响应和限流由认证模块统一处理 |
| 长期未验证账号 | 先不自动删除或释放邮箱；后续再明确清理周期，避免字段建设阶段引入自动删除 |
| 管理员邮箱换绑 | 新邮箱验证成功后，在受控流程中切换 User.email 与主邮箱记录；成功前保留旧绑定；同步更新联系资料时间，不把旧邮箱的已验证状态直接复制给新邮箱 |
| 联系资料全部清空 | 注册时两项都可为空；首次补齐后，普通资料编辑至少保留一种；关闭账号时的个人资料处理走管理员流程 |
| 关闭账号 | 普通关闭先处理未结束申请并完成退出/解散；紧急停用立即阻止登录并使会话失效，结束本人未完成申请及本人招募卡相关未完成申请，保留正式成员历史和原邮箱占用；完整已确认边界见[后续字段说明](database-fields.md#teams) |
| 手机号格式 | 字符串存储，允许携带国家区号；规范化规则与前端一致，不自动假定所有用户都是中国大陆号码，不将格式通过等同于号码归属已验证 |
| 学生管理员 | `is_staff=True` 配合必要用户组权限；不默认设为超级管理员 |

联系方式同步读取规则已确认。邮箱换绑涉及身份与联系信息同时变化，后端需把它作为单独流程实现，不能当作普通个人资料字段直接更新。

## 赛事

### 依据、范围与实施阶段

依据用户已审核的赛事设计范围、《创享科创信息与组队服务平台建设方案》《创享平台功能细则补充稿》《数据库开发交付要求》以及仓库 [产品范围](product-scope.md)。规则冲突时沿用较新的补充稿：学生自主组队只用于参赛，必须指向已收录的具体赛事届次。

赛事信息及其来源、分类标签用于后台维护和公开列表；队伍、招募、申请、成员、收藏和快讯模型均关联具体届次。科研机会独立建模，见[科研、资源、收藏和快讯](#content)。

| 对象 | 一条记录的含义 | 与赛事的关系 |
| --- | --- | --- |
| `Competition` | 一个具体赛事届次 | 赛事主体；后续业务关联这个主键 |
| `CompetitionSource` | 这个届次的一条官方或正式校内来源 | 赛事一对多来源，发布时恰好一个主来源 |
| `CompetitionTaxonomy` | 一个受控的分类或标签词条 | 每届一个主分类、零到多个标签；草稿分类可空 |
| 标签中间表 | 一届赛事与一个标签的关联 | 多对多关系，由 Django 管理 |

同一个年度存在春季、秋季两次独立参赛周期时，可分别设届次；同届不同赛道不另建赛事。首版没有独立的赛事系列表：未来需要跨届聚合页面时再增加系列模型，同时保留既有届次主键及业务关系。

### 身份、赛道与重复数据

#### 届次是业务关联单位

`title` 用于展示，`edition` 明示年度或届次，`code` 是稳定的内部导入标识。例如虚构赛事可用 `demo-robotics-2026`，展示名为“2026 年演示机器人挑战赛”。名称修改或报名延期时更新同一条记录；下一届创建新记录。

`code` 由建档流程指定，不能每次导入随机变化，也不能由会变动的标题自动重算。相同 `code` 重复导入应更新原记录并保留主键。唯一编码只能防止重复编码，不能自动识别两个不同编码实际属于同届赛事；录入或导入前仍需结合正式名称、主办方、届次和来源核对。发现碰撞时先停止覆盖，确认身份。

标题不能唯一，同一原文 URL 也不能作为全局赛事身份：一篇校内通知可能列出多项赛事，而一届赛事可能同时有官网公告、校内选拔和延期通知。

#### 赛道的首版处理

同届赛道写入 `tracks`，具体差异写入 `description`、`eligibility` 和 `deadline_notes`。只有各赛道确实共用的截止时间、团队人数和报名入口才填入主表的结构化字段。不能擅自取最早或最晚截止时间冒充全届统一截止。

如果后续需要按赛道筛选、自动计算分赛道招募资格，再增加归属于同一 `Competition` 的赛道表。届时同用户同届只能正式加入一个队伍的约束仍以届次主键判断。

### 公开内容与官方要求

#### 列表、详情及词条

- 列表主要读取名称、届次、简介、分类标签、赛事范围、各类截止日期、主来源及平台更新时间。
- 详情补充主办方、官方参赛资格、赛道差异、报名方式、作品提交要求、校内安排及所有已核验来源。
- `summary` 是简短介绍，`description` 是整理后的可阅读详情，两者均为纯文本。展示端按文本转义；首版不把 HTML 或任意富文本写入内容字段。
- 分类与标签由有权限的管理员维护；学生不能自行造标签。主分类只选一个，标签可多选。词条名称可调整，稳定编码与用途固定；停用后保留历史展示，阻止新增选择。
- `level` 仅记录来源明确的赛事范围。未注明填 `unknown`；不根据主办方名气推测“国家级”，也不代表同济认定等级。

词库属于运营数据，不把尚未审核的具体分类名称写成不可调整的数据库枚举。分类名与标签名不重复录入各条赛事；字段类型、词条结构和选择规则在本版固定。

#### 团队人数不是招募人数

`team_size_min`、`team_size_max` 只表示官方要求的参赛团队人数，均包含官方规定应计入的成员。未说明时用 NULL，不用 0；如果某赛道特殊，写明范围，不拼成误导性的全届上下限。

`participation_type=individual` 时两个团队人数字段为空且不能开放站内团队招募；`unknown` 不推断为团队赛。`both` 表示同届包含个人和团队参赛形式，并不允许个人赛参加者发布团队招募。

学生队伍现有人数、已线下确定的成员、待招人数、技能要求、投入时间、地点和目标均属于 `Team`、`Recruitment` 及其内容版本，不放入赛事主表。官方报名入口不等于站内入队入口；站内确认入队也不代表报名成功。

### 日期、精确时刻和未知信息

#### 三类截止事项独立保存

| 事项 | 日期字段 | 精确时刻字段 | 来源时区字段 |
| --- | --- | --- | --- |
| 官方报名 | `registration_deadline` | `registration_deadline_at` | `registration_deadline_timezone` |
| 作品提交 | `submission_deadline` | `submission_deadline_at` | `submission_deadline_timezone` |
| 同济校内报名或选拔 | `campus_deadline` | `campus_deadline_at` | `campus_deadline_timezone` |

`campus_arrangements` 必须解释校内截止具体针对什么事项、适用哪些院系或赛道。存在多个不同校内截止时，主表不强行选一个，完整保存于说明；将来需要自动处理时再拆独立时间节点表。

| 来源实际写法 | 保存与展示规则 |
| --- | --- |
| 没有给出日期，或仅“另行通知” | 日期、精确时刻为 NULL，时区为 `''`；展示“时间待通知/未提供” |
| 只写“2026 年 10 月 15 日截止” | 只填日期；不补午夜或当日最后一秒；明确展示“具体时刻未注明” |
| 写明“2026 年 10 月 15 日 18:00，北京时间” | 日期为 `2026-10-15`，保存对应带时区时刻，时区为 `Asia/Shanghai` |
| 写了时间但没有可确认的时区 | 保留完整原文信息于 `deadline_notes`，精确时刻留空；核实时区后再补齐 |
| 仅“10 月 15 日”，年份也无法从原文明示的上下文确认 | 不拼接当前年份；留空并记录待核验信息 |
| 不同赛道截止不同、分批报名或分阶段提交 | 在说明中分别保留；只有确属全届统一节点才填公共字段 |

精确时刻保存为带时区的时间点，按来源时区转换得到的日期必须与对应 `DateField` 一致。时区填写可解析的 IANA 名称或固定 UTC 偏移，不用含义不唯一的缩写。只有日期而来源明确时区时，可以保留时区；不知道则留空，不能把界面展示时区当作来源事实。

日期与精确时刻同时存储的目的是保留来源精度；所有写入路径必须一次校验并更新配套字段，避免改了日期而遗漏旧时刻。时间配套空值关系可以做数据库检查，时区解析与本地日期一致性由统一写入校验处理。

#### 状态和排序

- 日期为空是未知，不等于长期有效，也不能推断已经结束。
- 有精确时刻时可准确判断该节点“未截止/已截止”；只有日期时只显示“日期未到/今日截止日期/截止日期已过”，附“具体时刻未注明”。日期比较使用已知来源时区；未知时以页面北京时间作日历提示，不能据此开放招募。
- 截止尚未到不能单独证明“报名已开始”，因为首版没有统一报名开始时间；不输出没有依据的“报名中”状态。
- 最近发布按平台 `published_at` 降序、主键降序排列；临近报名截止视图排除已明确截止的记录，再按 `registration_deadline` 升序、空日期放最后、主键作稳定次序。已截止记录仍可通过公开历史查询。作品提交或校内截止使用各自筛选/排序，不混成一个不标事项的时间。
- 不硬性规定报名截止早于作品提交截止或校内截止早于官方截止；不同赛事可能有例外，异常提示核验即可。
- 当前 AI 提取仅提供 `YYYY-MM-DD` 日期和原文依据，可对齐两个日期字段；它不能提供或推算本方案的精确截止时刻，也不直接写库或发布。

### 来源、更新时间与发布校验

#### 来源分别保存

`CompetitionSource` 保存赛事官方及校内官方通知。每届最多一个 `is_primary=True`，发布时必须恰好一个。第一条来源建立后由写入流程明确设为主来源；切换时使用事务，先取消旧主来源再设新主来源。公开赛事更换主来源时必须在同一事务内完成最终校验。

同一赛事下重复的原文链接由导入流程规范化、匹配并更新已有来源；写入时锁定所属赛事，避免并发导入重复来源。规范化不能随意删除有意义的查询参数。来源链接不设置全局唯一；不同届次可以引用同一原文。发布校验要求公开返回的来源都已核验、确实适用于本届；未核验候选链接留在后续采集处理区，不作为正式公开来源。

原始发布日期和原文更新日期首版按日保存，字段名明确用 `_on`。不知道原始发布日期就留空，不用平台时间顶替；现阶段不为来源时间强加不存在的秒级精度。后续确需精确来源时间时，再增加精度明确的字段。

| 时间 | 含义 | 不能替代什么 |
| --- | --- | --- |
| `source_published_on` | 原通知发布日期 | 不等于平台发布或抓取日期 |
| `source_updated_on` | 原文明确的更新日期 | 不能用重新采集日期刷新 |
| 来源 `fetched_at` | 最近成功读取来源的时间 | 不代表人工核验，也不代表原文有更新 |
| 来源 `last_verified_at` | 此来源内容最近核验时间 | 不自动代表整届所有信息已核验 |
| 赛事 `last_verified_at` | 本条赛事整合信息最近核验时间 | 单纯保存、读取、重抓或 AI 生成不能刷新 |
| `created_at` / `updated_at` | 平台建档 / 内容修改时间 | 不能宣称是原通知发布时间 |
| `published_at` | 平台首次对公众发布的时间 | 更正、重新上架和原样导入不重置 |

源链接、时间、资格或报名信息变更时必须重新核验受影响部分并确认整条赛事的一致性；确认后再公开更正。未来自动化校验流程需要保留可追溯结果，不能仅让 AI 填一个时间就视为通过。

#### 发布所需信息

草稿只强制有稳定编码、标题和可识别的实际届次，其他字段按表中默认值建档。尚不能识别届次的原始材料属于待整理输入，不先伪造赛事届次。

从草稿发布或下架后重新上架时，统一校验以下内容；修改公开记录也适用，不能通过 Admin、导入脚本或批量更新绕开：

1. 标题、届次、简介和详情非空，内容能识别该届赛事；首次或重新发布时主分类为启用的分类词条。公开记录的一般更正可保留既有停用关联，但不能新增选择停用词条。
2. 恰好一个主来源；所有公开来源名称和 URL 合法，并有核验时间；整条赛事也有核验时间。校内安排须有支持其内容的校内来源。
3. 数字、枚举、文本长度、词条用途、日期和精确时刻配套关系全部合法。
4. 缺失资格、人数或截止日期保持未知并在页面说明，不因个别非核心字段缺失而猜填，也不因此一律禁止发布。
5. 如果同时启用平台招募，额外通过下一节的招募条件校验。

词条停用只阻止新增选择，不立即隐藏历史赛事；既有公开内容继续展示原词条。后续重新发布时更换为启用词条。

#### 发布状态

| 当前状态或操作 | 处理规则 |
| --- | --- |
| `draft` | 仅授权维护人员可见；`published_at` 为空 |
| 首次发布为 `published` | 核验通过，在同一事务内写入首次发布时间 |
| `published` 内容更正 | 保留首次发布时间；核验更正内容并更新内容更新时间 |
| 从 `published` 下架为 `withdrawn` | 必填内部下架原因，并关闭招募开关；公共列表与详情停止返回；既有队伍和成员关系保留 |
| `withdrawn` 重新发布 | 重新通过发布校验；保留首次发布时间与最近一次下架原因，原因仍不公开 |
| 报名或作品提交截止经过 | 不自动改为草稿或下架；仍可作为公开历史被检索 |

首版不增加独立的 `archived` 发布状态，不支持将已发布过的记录退回从未发布的草稿。下架记录必须有曾经发布的时间；首次发布前的弃用草稿保持草稿或按删除条件处理。`withdrawal_reason` 只记最近一次原因，完整状态历史由 AdminAction 记录，不能把这个字段宣称为完整审计记录。

公开返回由服务端以 `publication_status=published` 过滤；草稿和下架的详情请求同样不得泄露内容。`code`、维护人、下架原因、招募核验说明、采集时间等内部字段不进入公开字段白名单。

### 与队伍和招募卡的衔接

赛事决定这一届的官方条件和站内招募上限；学生队伍及卡片表达具体团队的需求。使用以下关联路径，避免冗余字段不一致：

| 后续对象 | 关联方式与职责 |
| --- | --- |
| `Team` 队伍 | `competition` 外键关联本届 `Competition`，使用 `PROTECT`；保存队伍及成员规模，正式关联后不随意换届 |
| `Recruitment` 招募卡 | 外键关联 `Team`，经队伍取得赛事届次；保存岗位、要求、名额、卡片期限；同队最多一张有效卡 |
| `Application` / 成员关系 | 关联具体招募或队伍；同用户同届只能正式加入一个队伍，由后续成员模型及入队事务保证 |
| 收藏 / 快讯引用 | 关联届次主键；记录过期或下架不能造成悬空引用，保留和展示规则见[内容模块](#content) |

#### 赛事侧开放招募的条件

赛事创建时 `recruitment_enabled=False`、`recruitment_deadline=NULL`。管理员启用前需确认：

1. 赛事处于公开状态，官方允许相应团队参赛，`participation_type` 为 `team` 或 `both`。
2. 已明确可以组队的适用范围和期限，填写带时区的 `recruitment_deadline` 及内部 `recruitment_note`；启用时期限必须晚于当前时间。来源只给了日期或时区不清时，先核实或确认一个有依据的、更早的平台停止招募时刻，不能把日期自动补到 23:59:59。
3. 平台期限不晚于适用于这些队伍的官方组队、报名或校内选拔限制。不是机械取所有日期中的最小值，也不把作品提交截止当作当然可以组队到该时刻的依据。
4. 涉及多个赛道且还不能结构化判定各自资格时，只在能核实全届统一开放条件与期限时启用；否则保持关闭，赛事仍可公开浏览。

新卡片选择 3、7、14 天期限，实际到期取所选时长与赛事招募截止的较早者；临近截止仍保留全部选项，发布前展示实际截止时刻。编辑不延长原卡有效期。

是否现在允许招募应实时结合发布状态、开关、截止时刻和用户的邮箱验证、联系方式、限制状态判断。赛事下架、关停招募或超过平台招募截止时刻后，即使旧卡片还留在数据库，也必须停止新发卡和新申请；保留已正式加入的成员、已有成员联系权限和退出处理。同时终结尚未完成的申请、撤销其联系权限，不再允许继续接受或确认入队；已正式成员的关系与双方联系权限保留。既有队伍不因招募卡过期而消失。

组队的版本、人数与生命周期见[队伍与招募](#teams)；同届唯一成员由成员表约束和入队事务共同保证。

### 约束放在哪一层

数据库约束负责底线，统一写入流程负责跨表与业务校验。Django `save()` 本身不会自动执行完整模型校验，不能只写字段说明或 `clean()` 就认为所有入口都已受保护。

| 层级 | 应落实的规则 |
| --- | --- |
| 数据库唯一约束 | 赛事 `code` 唯一；词条 `code` 唯一；同用途词条名称唯一；每届至多一个主来源的条件唯一约束；标签中间表的赛事与词条组合唯一 |
| 数据库检查约束 | 枚举取值合法；必填字符串去空白后非空；编码格式；人数为空或至少 1，最小人数不大于最大人数；个人赛团队人数为空且不开招募；日期与精确时刻、时区的基本空值配套；草稿无发布时间，公开或下架状态有发布时间；下架原因非空；启用招募时必须已公开、形式合法且期限和说明齐全 |
| 模型及统一服务校验 | 文本长度及 URL 协议；时区解析、精确时刻与来源日期一致；词条用途；发布前分类和来源核验；跨来源的信息一致；招募期限依据；首次发布时间及固定编码不可被随意改写 |
| 事务和并发处理 | 发布/下架及重新发布；主来源切换；按稳定编码导入及来源去重；时间配套修改；后续入队人数与同届唯一队伍校验 |
| 权限与接口 | 仅授权人员维护官方赛事；公众只读公开字段；维护人由服务端确定；不信任客户端传入的审核时间或发布权限 |

发布条件中的“恰好一个主来源”、分类/标签用途等跨表规则不能只靠普通 `CHECK` 约束完成，必须由统一入口在事务结束前验证。发布中的来源和标签修改也要走这个入口。变更数据的导入命令、Admin 和将来的 API 共用规则；不要使用绕过规则的任意 `QuerySet.update()` 或批量写入。

`updated_at` 在主表普通保存时自动更新，但来源和多对多关系的变化不会天然触发主表保存；实现时应由统一写入服务显式更新它。只有抓取时间或核验时间变化、内容没有变化时，限定保存字段，不更新主表 `updated_at`。重复导入内容完全相同的数据保持原样。

索引基线：保留主键、外键和唯一约束产生的索引；增加 `(publication_status, published_at, id)` 与 `(publication_status, registration_deadline, id)`，支撑公开列表和报名日期排序。其他索引按实际接口查询增加，不给长 URL 建无依据的索引。

#### 删除规则

已发布过或已被队伍、收藏、快讯等业务引用的赛事不硬删除，采用下架保留身份。只有从未发布且无业务引用的草稿可由授权管理员删除，所属来源随之清理；后续业务外键使用保护策略。分类和标签被引用时不硬删除，通过停用管理；标签侧需在删除入口显式检查引用，不能依赖默认多对多级联保留历史。

维护用户被删除时 `created_by`、`updated_by` 置空，赛事不被级联删除；用户禁用不影响已有维护记录。首版这些字段只提供最近维护信息，完整操作追溯由 AdminAction 与相关事件记录承担。

<a id="competition-implementation"></a>

### 赛事模型实现边界

已实现三张模型及标签多对多关联、字段验证器、数据库约束定义和查询索引；模型 `full_clean()` 检查来源日期与精确时刻一致、主分类用途、发布所需来源和核验字段、首次发布时间与稳定编码等。标签关联的标准 `add` / `set` 入口会拒绝分类和停用标签；被使用的词条与曾经发布的赛事受到删除保护。

赛事模型保留 Django 标准的 `save()` 行为，不隐式执行跨表发布流程。后端需提供统一事务写入入口，在保存前调用 `full_clean()`，并锁定相关记录、管理主来源切换、标签和来源更新时的赛事时间戳、下架开关、首次发布时间及操作者。`objects.create()`、批量更新、直接写标签中间表等都不能替代该入口。真实来源可信度、招募期限依据和权限也由业务流程保证；模型无法从一段核验说明自动判断这些事实。

<a id="teams"></a>

## 队伍、招募与成员

### 团队、招募轮次与人数

`Team` 表示某一赛事届次中的平台队伍；招募者也是正式成员，通过 `Membership(join_source=recruiter)` 记录。创建队伍与招募者成员关系必须在同一事务完成。每人同届赛事最多一个有效成员关系，条件唯一索引同时覆盖招募者和应募成员。

`Recruitment` 是一轮招募的稳定身份，编辑不更换 ID。`RecruitmentRevision` 是不可修改的内容版本，每次实际编辑递增。草稿先创建卡片和版本、装配多选及基数成员，再校验并发布。公开且未关闭的卡片每队只能有一张，满员和解散等待中的卡仍占这个位置。到期必须在锁内结算为已关闭后才能另发，不依赖后台任务准时运行。

`existing_member_count` 为招募者声明的已有总人数，包含招募者以及无需逐个建账号的线下成员；`recruitment_quota` 为本轮还计划从平台招募的人数。初次发布 quota 至少为 1，后续编辑允许降到 0，但不能少于本卡仍有效的成功应募人数。声明已有总人数也不能少于平台已知的基数成员数。官方存在团队人数上限时，声明已有数加 quota 不得超出上限；平台无法核实未注册成员身份，不虚构其个人记录。

每个卡片版本通过 `RecruitmentBaselineMember` 记录已计入声明人数的有效平台成员，排除通过本卡加入的人。后来这些成员退出，展示已有数随之减少；不会自动放大本轮 quota。例如已有 4 人、计划招 1 人，老成员退出后显示已有 3 人、仍计划招 1 人。招募者若想补招，可编辑成已有 3 人、计划招 2 人，并触发正常版本与通知流程。本卡应募成员退出则减少本卡成功人数、释放本卡名额；只在原卡仍有效时恢复可申请状态，不复活已结束的申请。

### 招募卡编辑与挂起

允许调整人数、能力、角色、技能、基础、投入和合作信息；赛事和招募者不能在原队伍上替换。3/7/14 天在发布时选择，实际 expires_at 取发布时刻加所选期限与赛事招募截止的较早者。编辑不延长期限，也不修改首次发布时间。

每次真正的招募者内容变更，在同一事务完成以下操作：

1. 锁定队伍与卡片，结算到期状态，校验名额、基数和官方上限；解散等待期间拒绝编辑。
2. 建立下一版内容、选项和基数快照；无实际变化则不生成版本。切换 current_revision，写 last_edited_at，保留旧版本及申请。
3. 记录 `recruitment_edited` 事件，payload 只含旧/新版本号和变更字段键；展示时由两个版本生成轻量差异，不存用户联系方式。
4. 向所有未结束申请人和当前平台成员发送站内通知，按用户去重；已入队成员身份不变，未结束申请因为版本不一致而挂起。

挂起期间仍可撤回或选择继续；未选择一直挂起，不默认同意。已读消息只改 read_at。继续时建立新的 ApplicationRevision 接受当前卡片版本，可同时调整选填角色/技能和必填投入，清空双方旧的正式确认；历史确认由事件保留。再次编辑再次挂起。满员、到期、关闭、下架、赛事停招、加入同届另一队等正常终结条件仍处理挂起申请。

### 申请、联系方式和正式入队

申请初始 `pending`；提交代表申请人愿意向招募者开放联系方式，招募者答应后转 `contact_open`，记录 contact_opened_at，双方互相看到学校邮箱及已填微信/手机号。该动作不占名额，也不等于招募者正式确认入队。平台不提供聊天记录或聊天功能。

联系资料只从当前 User 读取。仅当事双方按关系权限可见；其他队员不因此获得整队通讯录。申请挂起不撤销已获得的联系权限，尚未获准的挂起申请不能新增开放。申请结束后隐藏；正式成员在有效关系期间保留双方联系权限，退出或解散后隐藏。联系更新不改卡片版本。

申请人和招募者分别正式确认当前 ApplicationRevision。第二方确认时，服务在同一事务重新读取当前卡片版本、队伍状态、剩余名额、赛事及账号条件；两方确认都针对现版且有效才创建 Membership，并将申请设为 joined。数据库一对一防止同一申请重复入队，成员条件唯一防止同届重复入队；容量需锁住卡片后计数，不能仅靠 full_clean。

同一用户对同一卡片终身只有一条 Application，拒绝或撤回后不能再次提交；新卡可重新申请。可以同时申请同届多队，成功加入一队后终结其他未完成申请。招募者同样受同届成员唯一限制。申请人可在正式加入前撤回，招募者可拒绝或结束已开放联系但尚未入队的申请；双方在完成入队前可撤销自己的确认，撤销不自动终结申请。申请的 joined 是历史成功结果，之后退出只结束 Membership。

状态与结束原因分开：pending/contact_open 的 resolved_at 为空且 end_reason 为空；joined/withdrawn/rejected 使用对应同名原因；ended 使用满员、到期、卡片关闭/下架、停招、加入其他队伍、队伍解散、账号停用或招募者终止等允许原因。暂停是派生条件，不覆盖原阶段。

### 退出、移除和解散

退出与移除共用 DepartureRequest：exit 是成员发起、招募者回应，removal 方向相反。每个成员关系最多一个 pending 请求，招募者不能对自己使用该流程。固定 24 小时；agree → approved 并结束成员，reject → rejected 且成员保留，无回应到期 → timed_out 并结束成员。pending 没有回应或结束时间；approved/rejected 有真实回应及回应时间；withdrawn/timed_out/team_dissolved 无虚构回应且有结束时间。拒绝后的请求不能被超时任务转为同意，重新提出可新建请求。发起人在截止前可撤回，不要求填写自由理由。

解散由招募者发起 DissolutionRequest，当时其他平台正式成员各有一条 DissolutionResponse。全部同意即可完成；任何有效拒绝立即结束为 rejected 并保留队伍；到期仍无人拒绝则 completed/timeout。仅招募者一人时明确确认后 completed/no_other_members。pending 时可在截止前撤回。回应只有一次，不记录超时为假同意。

解散等待中阻止新增申请、入队和卡片编辑，但不重置卡片有效期、删除记录或停止正常离队。个别成员先正常离队时，其待回应行以 excluded_at 排除，不伪造 agree。解散完成需一次事务：结束全部有效成员（含招募者）、关闭卡片、终结未完成申请、终结未完成退出/移除请求并标 team_dissolved、通知所有当事人。历史保留；旧队伍不恢复。拒绝/撤回只解除本次等待，不能复活自然到期或已结束业务，也不能消除另一个“卡片版本未接受”的暂停原因。

<a id="content"></a>

## 科研、资源、收藏和快讯

科研发布人工必填只有标题与介绍/原文、招募主体、官方信息链接；其余全部可选。主体可为非结构化文字，不强制导师、院系、名额、申请方式、核验材料都拆字段。官方信息链接不必是直接报名入口。未知数值使用 NULL，未知日期不补造时刻；fixed 需来源明确日期，unknown/ongoing 不填写精确截止。同课题下一批另建机会。长期/截止未知且未结束的项目按最近核验时间（无则首次发布）加 30 天标待复核，不自动宣称招募结束，也不进入“已核验且仍有效”候选。

资源只保存外链；发布需名称、介绍、类别、访问链接。失效仍公开历史但停用访问按钮，下架则隐藏内容。科研与资源都有内容版本快照，选项展示名和来源按当时版本保存；JSON 使用允许的公开内容字段白名单，内部核验说明和用户联系方式不向公开接口返回。

收藏只有赛事、科研、资源三类且目标恰好一个外键；每用户每目标唯一。登录即可使用，无额外邮箱验证要求，仅本人可读。取消删除关系；目标下架时返回“内容不可用”占位，不泄露标题正文，恢复同一目标后可再次展示。不订阅推送。

快讯主表只指向已确认 NewsletterRevision，草稿另存，已确认版本和内容项冻结。每期最多一个草稿，确认时需标题和至少一个完整内容项；修订先复制草稿，再人工确认切换。保留首次发布并记录最后编辑。每项只能关联相应赛事/科研/资源，或作为无目标外键的活动段落；活动不建独立管理模型。标题摘要采用当期快照，来源后来更新只提示，不覆盖历史；来源下架后，公开当前及历史快讯均隐藏该项所有内容。资源失效提示同样由当前目标计算。无自动邮件或微信群发送。

## 消息、治理与账号

BusinessEvent 保存动作和必要版本/原因，Notification 保存每个接收人的站内消息；数据库唯一 `(event,recipient)` 防止重复通知。event_key 为同一动作重试复用的 UUID，服务需验证重试的动作和目标一致，不能拿新 UUID 规避幂等。事件、状态和收件人一起提交；无需发送外部邮件。通知对象限申请双方、相关成员及管理处理当事人，点击时重查权限，不信任历史快照的访问资格。确认/撤销/继续等事件用于追溯，并非每条都再通知本人。

`recruitment_*` 指向卡片；申请/联系/入队事件指向申请；`departure_*`、`dissolution_*` 各指向请求；`admin_action` 指向管理记录。payload 为固定键集：版本号、变更字段列表、确认方、结果原因等，不接受任意客户端 JSON。通知正文是系统模板文本，不接受私聊投稿，不自动删除已读记录。

治理只保留 AdminAction 与既定 UserRestriction，不建立举报、申诉、反馈次数或工单模型。“联系我们”采用运营配置的官方联系入口，实际地址由运营提供，不虚构邮箱。管理员统一处理；撤销操作追加新记录并指向旧记录，不覆盖审计历史。

限制固定 24 小时，重复操作返回原有效限制，不叠加、不重置，可提前解除并保留理由。只阻止新发布招募和新提交申请，不一概禁止处理已有关系。普通账号停用先结束申请并完成退出/解散；紧急停用立即阻止登录并使会话失效、关闭本人招募卡和相关未完成申请，保留正式成员历史，其他人仍可依 24 小时机制离队。恢复账号不自动恢复旧卡旧申请。

<a id="ingestion"></a>

## 采集与 AI 追溯

SourceConfig 保存管理员允许的来源和适配器标识，不保存代码或密钥；每 6 小时和手动触发属于后端任务配置。FetchRun 记录结果而不复制完整请求响应。相同 `(source,source_url,content_hash)` 复用 SourceVersion 并更新 last_seen_at；哈希取规范序列化的标题、正文、来源日期和来源时间原文，内容变化形成新版本。抓取时间不能冒充官方发布日期。

ProcessingResult 保留结构化候选、字段证据、缺项和校验错误，AI 输出不等于发布。科研与快讯必须人工确认；赛事只有完整通过既定规则才允许 rules 决策，并保存规则版本。快讯结果被采纳也只是生成草稿。ProcessingInput 固定当次快讯引用内容与顺序，每次最多 10 条、标题正文合计不超过 20000 字符；活动人工维护。AICall 只记模型、提示版本、耗时、用量和脱敏错误，不存密钥、联系资料或完整原始请求响应。被引用的来源/结果/调用保留；只允许清理无引用且结束超过 30 天的详细任务/调用日志。

<a id="transactions"></a>

## 事务与接口约定

模型 `full_clean()` 校验字段和可见的跨表关系；QuerySet.update、bulk_create、M2M.add 和直接 SQL 不执行它，多选写入应校验显式 through 模型。数据库约束只保证可表达的同一行、唯一性与外键条件。不可变版本、权限、收件人完整性、当前人数、24 小时截止处理和跨表联动都必须由受控事务入口保证，不能直接把任意模型写入暴露为 CRUD API。

统一按“受影响用户按 ID 排序 → 赛事 → 队伍按 ID 排序 → 卡片 → 申请 → 成员/请求”获取 select_for_update 行锁；加入同届另一队时先列齐受影响队伍再按序加锁，查询结果须锁内重新检查，避免两个确认同时占最后名额或反向锁死。一个固定 now 用于同次操作，先结算已到期请求/卡片，再判断本次动作。定时任务和用户入口复用结算逻辑，拒绝和撤回后的请求不能重开；任何越过时限的回应不得改写已生效的超时结果。数据库唯一失败整体回滚并映射成明确业务冲突，不能提交半个入队/半组消息。

新发布/申请还必须校验学校邮箱验证和联系资料门槛。邮箱验证的业务规则、allauth 唯一状态来源已确认，但 allauth 安装与 Headless 路由、验证码具体参数、发信配置及真实学校邮箱收件尚未实现；参见[邮箱验证实施说明](backend-development.md#email-integration)。本轮建表不代表注册验证接口、Admin 界面、定时任务或全部业务接口已上线。

| expected_duration | 空串：未指定；`up_to_1_month`：1 个月以内；`over_1_to_3_months`：超过 1 至 3 个月；`over_3_to_6_months`：超过 3 至 6 个月；`over_6_months`：超过 6 个月 |
| collaboration_mode | `online`：线上；`offline`：线下；`hybrid`：混合；科研额外允许 `unknown`：未说明 |
| Application.status | `pending`：待招募者答应沟通；`contact_open`：已开放联系方式，待入队确认；`joined`：已成功入队；`withdrawn`：已撤回；`rejected`：已拒绝；`ended`：因其他确定原因结束。挂起另由版本与解散状态计算 |

<a id="acceptance"></a>

## 验收边界

字段表确定的是持久化含义，公开接口的 URL、字段组织、来源嵌套方式、分页参数、筛选参数和错误格式仍需在 [API 说明](api.md) 中与实现一同落定。接口用白名单序列化，不能直接返回整张模型表；精确时刻采用带偏移的 ISO 8601，日期采用 `YYYY-MM-DD`，未知值保持 `null`。

| 阶段 | 应覆盖的案例 |
| --- | --- |
| 用户模型与数据库 | 正常创建用户；空邮箱拒绝；大小写不同的重复邮箱拒绝；绕过表单写入也不能制造重复；密码不以明文保存；系统代号唯一且不可由普通用户改写；未补联系方式仍能创建账号 |
| 联系资料与组队接口 | 微信、手机号仅填一项或同时填写均可；两项都空不能发布或申请；资料修改后有效联系对象读取最新值；公开接口及无联系权限对象拿不到这些字段；关系结束后不再返回 |
| 邮箱与登录 | 新账号未验证；未验证仍可登录但不能发布或申请；正确验证后以 allauth 状态为准；换绑不能继承旧邮箱的验证结果 |
| 业务限制 | 同时拦截新增发布和申请；保留已有记录、退出及通过统一入口联系管理员的能力；24 小时边界前后判断正确；提前解除立即恢复相应能力；重复管理员操作不意外延长处罚 |

模型与数据库已经完成本机验证；接口权限、跨表事务、并发处理、定时结算、Admin 表单和学校邮箱收件仍需后端接续验收。SMTP 密码、Django 密钥和第三方 API key 属于环境配置，不写入业务表。
